本规范把规格驱动开发（Specification-Driven Development，SDD）和测试驱动开发（Test-Driven Development，TDD）定义为 Research Scout 的工程门禁，而不是建议性流程。规范中的“必须”“不得”为强制要求，“应”“可以”为默认要求；偏离强制要求必须有获批的 ADR 或在本规范中完成修订。

---

## 1. 目标

Research Scout 的实现必须同时满足四个条件：

1. **可追溯**：每项行为都能回溯到 PRD、架构、设计、OpenAPI 或一份已批准的变更规格。
2. **可验证**：每个验收条件都有自动化测试，或明确记录不可自动化的原因和替代验证证据。
3. **可回归**：修改不能依赖人工记忆，外接 Provider、数据库和用户旅程都必须有稳定的合同或集成测试。
4. **可维护**：代码结构、迁移、契约和文档共同演进，不形成“代码是事实、文档已过期”的状态。

执行原则：

- SDD 决定“为什么做、做什么、不能做什么、如何验收”。
- TDD 决定“如何证明行为正确、如何推动最小实现、如何防止回归”。
- 文档、规格、测试和生产代码都是交付物，不能在实现完成后补写。
- 小步提交垂直切片，不一次实现多个互相依赖但无法独立验收的模块。

## 2. 不可协商的工程约束

以下规则适用于本地开发、CI、人工评审和所有编码 Agent：

1. 没有已批准的变更规格（Change Spec）和可测试验收条件，不得开始业务代码实现。
2. 没有先观察到失败测试，不得把新行为标记为实现完成；测试必须先编码规格，再推动实现。
3. 不得通过删除断言、放宽断言、跳过测试、修改 fixture 或标记 flaky 来让流水线变绿。
4. 不得静默改变产品行为。产品行为变化先更新 PRD；架构边界变化先新增 ADR；接口或数据变化先更新设计和 OpenAPI。
5. 不得在任何仓库文件、日志、测试快照或 Agent 输出中写入真实 API Key、Zotero 私人全文、真实 PDF、未脱敏响应或生产数据。
6. 每次读取和写入业务数据都必须先应用 `workspace_id`、生命周期和当前版本过滤；租户隔离是功能，不是后续加固项。
7. `metadata_only` 永远不能成为科学结论证据；`web_context` 不能单独支撑科学事实；来源不足必须显式降级，不得伪装覆盖。
8. v1 不引入 Connector、Local API、OIDC、group library、PDF 上传/解析、Zotero 写回或 Tavily 默认依赖。
9. Agent 不得在没有用户明确要求时执行 `git commit`、`git push`、创建 PR 或改写历史。
10. 任何“先临时绕过，之后再补测试”的实现不得合并。限时 spike 可以存在，但必须隔离、不可直接合入，最终实现重新走 TDD。

## 3. 事实源与变更分类

### 3.1 事实源优先级

出现冲突时，按以下优先级处理：

1. PRD：产品范围、用户行为、成功标准和产品级边界。
2. 架构基线与 ADR：系统边界、技术选型、依赖方向、部署方向。
3. 技术设计包：模块接口、数据模型、状态机、检索与运行时细节。
4. OpenAPI：HTTP 路由、请求/响应、错误和 SSE 事件契约。
5. Change Spec：本次变更的局部规格、验收条件和测试映射。
6. 代码与测试：事实源的具体实现，不得反向覆盖上游承诺。

发现冲突时，先停止扩大实现范围，更新正确层级的事实源，再继续。不得用代码中的特殊分支掩盖规格冲突。

### 3.2 变更类型与必需产物

| 变更类型 | 必须先更新的内容 | 最低验证 |
|---|---|---|
| 产品行为、范围、证据规则 | PRD；必要时同步架构/设计 | PRD 验收条件 + 自动化场景 |
| 架构边界、依赖方向、关键选型 | ADR + 架构基线 | ADR 评审 + 对应合同/集成测试 |
| 模块接口、数据模型、状态机 | 技术设计包 + Change Spec | 单元/集成/数据库测试 |
| HTTP 或 SSE 契约 | 技术设计 + OpenAPI + Change Spec | OpenAPI lint + API 合同测试 |
| 仅实现内部重构 | Change Spec | 行为保护测试 + 完整回归 |
| 缺陷修复 | Change Spec（可轻量） | 先写复现测试，再修实现 |
| 文档修正 | 相关文档 | 链接、术语、版本和差异检查 |

### 3.3 规格 ID 与目录

实现代码后，变更规格统一存放于：

```text
docs/changes/RS-SPEC-<四位序号>-<slug>.md
```

示例：

```text
docs/changes/RS-SPEC-0001-stage0-smoke-test.md
```

一个规格只解决一个可独立验收的结果。若需要多个团队并行实现，必须拆分成有明确依赖关系的多个规格，而不是共享一份无法独立关闭的巨型规格。

## 4. SDD 工作流

### 4.1 生命周期

```text
Draft -> Ready -> Implementing -> Verifying -> Done
             \-> Abandoned
```

| 状态 | 进入条件 | 允许动作 |
|---|---|---|
| `Draft` | 已发现问题，尚未冻结范围 | 调研、澄清、补规格；不得写业务代码 |
| `Ready` | 规格字段完整，验收条件可测试，依赖和风险明确 | 可以写失败测试并开始实现 |
| `Implementing` | 第一个 Red 测试已提交到工作区并确认失败 | 逐步 Green、Refactor；不得扩大未声明范围 |
| `Verifying` | 所有验收条件已实现，正在跑完整验证 | 修复回归、补文档、整理证据；不得悄悄改行为 |
| `Done` | Definition of Done 全部满足并有证据 | 可合并、部署或进入下一规格 |
| `Abandoned` | 明确不再实施 | 记录原因；保留已确认的决策引用 |

状态只能向前推进。重新扩大范围或改变验收条件时，必须退回 `Draft`，更新规格后再重新进入 `Ready`。

### 4.2 Ready 门禁

Change Spec 进入 `Ready` 前必须满足：

- 有唯一 ID、标题、状态、负责人和日期。
- 有明确问题、用户或系统收益，以及不做什么。
- 列出受影响的模块、接口、数据、迁移和文档。
- 每项验收条件都有唯一 ID，并描述可观察结果。
- 测试计划把每个验收条件映射到具体测试层级和测试标识。
- 已识别租户隔离、隐私、日志、Provider 降级、迁移和回滚影响。
- 没有会改变实现方向的未决问题；非阻塞问题必须写明默认值和最迟决策点。
- 与 PRD、架构、设计包和 OpenAPI 无已知冲突。

### 4.3 追踪规则

每个实现任务必须形成可审查的追踪链：

```text
Spec -> AC -> Test -> Code -> Verification Evidence -> Done
```

最低要求：

- 每个 `AC-xxx` 至少映射一个测试。
- 每个行为变化至少有一个“旧行为会失败、新行为会通过”的测试。
- 数据库迁移至少有一个迁移集成测试和一个数据兼容场景。
- OpenAPI 变化至少有一个 schema/contract 测试。
- 成功路径和关键异常路径都必须有覆盖；不能只测 happy path。
- 不允许出现“测试通过但没有任何验收条件引用该测试”的关键行为测试。

### 4.4 实现中发现规格缺口

实现过程中发现规格不完整时：

1. 停止继续添加未声明行为。
2. 记录实际发现、影响范围和可选决策。
3. 更新 Change Spec；如影响产品或架构，再向上更新对应事实源。
4. 重新执行 Ready 门禁。
5. 新增或修改失败测试，然后继续实现。

不得为了保持“代码已经写完”而反向修订规格，使其只描述现有实现。

## 5. TDD 工作流

### 5.1 基本循环

每个验收条件按以下循环推进：

```text
Red -> Green -> Refactor -> Re-run -> Evidence
```

1. **Red**
   - 从最小可观察行为写测试。
   - 运行最窄测试命令。
   - 确认失败原因是缺少目标行为，而不是测试自身错误、fixture 缺失或环境故障。
   - 记录命令、测试标识和失败摘要。
2. **Green**
   - 只写让当前测试通过的最小实现。
   - 不提前实现尚未进入验收条件的扩展。
   - 运行同一测试和相邻模块测试。
3. **Refactor**
   - 在测试保持绿色的前提下消除重复、澄清命名、收紧接口和改善结构。
   - 重构不得改变验收行为；若改变行为，返回 SDD 更新规格。
4. **Re-run**
   - 运行受影响模块、数据库集成和相关合同测试。
   - 完成后再运行仓库级验证。
5. **Evidence**
   - 在 Change Spec 或 PR 中记录 Red、Green、完整验证命令及结果。

### 5.2 强制测试先行范围

以下工作必须测试先行：

- 领域规则、状态机、scope、证据分层、缺口判定。
- Zotero 同步、游标、幂等、删除和重试。
- 数据库查询、事务、迁移、FTS、pgvector、RRF 和清理任务。
- HTTP/SSE 契约、身份适配器、错误映射和跨 workspace 隔离。
- Provider 适配器的解析、超时、限流、降级和错误分类。
- React 交互状态、关键表单、错误恢复和可访问性关键路径。
- 缺陷修复中的复现条件和回归保护。

### 5.3 例外

只有以下工作可以不为“测试先行”阻塞：

- 纯文档、注释、格式化和不影响行为的静态资源调整。
- 一次性 spike，用于验证未知技术；必须有时间盒，且不得作为生产代码合入。
- 由工具生成的代码；生成器输入和生成结果仍必须有合同或 smoke test。
- 紧急生产恢复。允许先恢复服务，但必须在同一工作日补复现测试、事故记录和长期修复规格。

例外只能豁免“先看到 Red”的时序，不能豁免最终的行为验证。

### 5.4 测试设计规则

- 测试名称描述行为和条件，例如 `TestEvidenceEligibility_MetadataOnly_ReturnsFalse`。
- 优先断言对外行为，不依赖私有实现、调用顺序或日志文本。
- 使用最便宜的测试层级覆盖行为；不要把单元规则全部放到 E2E。
- 外部 Provider 在单元和 CI 合同测试中使用固定 fixture 或 stub；默认 CI 禁止真实网络。
- 时间、随机数、ID、游标和并发调度必须可注入，测试必须确定性。
- 时间统一使用 UTC；禁止依赖本地时区和测试执行顺序。
- 禁止 `sleep` 等待异步结果；使用显式状态、fake clock 或带上限的轮询。
- 测试必须可并行安全，或明确声明不可并行及原因。
- Mock 只模拟边界；领域逻辑不能被 mock 掉。
- 失败信息必须包含可诊断上下文，但不得包含私人全文、密钥或未脱敏请求。
- 回归测试必须能证明修复前失败；只新增一个“永远通过”的测试不算回归保护。

### 5.5 测试层级

| 层级 | 目标 | 默认工具/方式 | 运行时机 |
|---|---|---|---|
| 单元 | 纯领域规则、状态转换、错误映射 | Go `testing`；Web `Vitest` | 每次保存/提交，最快反馈 |
| 组件 | React 状态、表单、错误和可访问性 | Vitest + Testing Library | Web 提交前 |
| 数据库集成 | 迁移、事务、约束、FTS、pgvector、并发 | testcontainers + PostgreSQL/pgvector | 影响持久层时及 CI |
| Provider 合同 | Zotero/S2/OpenAlex/Qwen 的解析和故障语义 | 脱敏 fixture、stub、schema 校验 | Provider 变化及 CI |
| API 合同 | OpenAPI、幂等、分页、错误、SSE 重连 | OpenAPI lint + HTTP 合同测试 | API 变化及 CI |
| E2E | 首次连接、同步、三种检索、证据追溯、清理 | Playwright + 本地 stub | 主流程合并前 |
| 安全/生命周期 | workspace 隔离、日志脱敏、tombstone、30 天清理 | 授权矩阵 + 集成测试 | 安全边界变化及 CI |
| 检索质量 | 引用可追溯、证据分层、缺口判定 | 合规小型 golden set | 检索/Agent 变化时 |

### 5.6 覆盖率

覆盖率是辅助指标，不是行为正确性的替代品：

- 新增或修改的核心领域包行覆盖率不得低于 80%。
- 同步状态机、scope 过滤、证据资格、生命周期和权限判断的每个分支都必须有测试。
- 不以全局覆盖率掩盖新增核心代码未测试；CI 应输出 changed-package coverage。
- 不得为了提升覆盖率写无断言测试、只调用不验证的测试或重复测试。

## 6. 模块专项规则

### 6.1 OpenAPI 与 HTTP

- 先更新 OpenAPI 和设计文档，再实现路由。
- OpenAPI 必须通过 3.1 lint；请求、响应、错误和 SSE payload 使用统一 schema。
- 路由 handler 不直接访问数据库，不自行拼接租户条件。
- API 行为必须有合同测试；错误码、幂等键、分页和时间字段必须与设计一致。
- SSE 事件必须持久化 `{id, seq, type, at, data}`，支持 `Last-Event-ID` 重放测试。
- 不添加隐藏推理、内部提示词、堆栈或未脱敏 Provider 响应字段。

### 6.2 数据库与迁移

- 已应用的 migration 不得修改；修复必须新增 migration。
- 生产迁移采用 expand/contract，破坏性删除不得与停止使用旧结构的代码在同一发布阶段完成。
- 每个迁移必须从空库执行通过，并覆盖从“上一个已发布版本”升级的真实路径。
- 约束、唯一键、外键和 tombstone 是幂等的一部分，不能只靠应用层判断。
- 测试必须覆盖并发重复写入，不允许依赖单线程假设。
- 备份恢复后必须重放 tombstone，测试并避免了已删除对象复活。

### 6.3 Provider 与外部来源

- 先定义领域接口和错误语义，再实现具体 SDK 或 HTTP adapter。
- 每次外部调用必须显式设置超时、重试边界、限流和取消传播。
- 429 必须遵守 `Retry-After` 或退避策略；不得无限重试。
- Provider 错误映射到稳定领域错误，不把 SDK/HTTP 类型泄漏到领域层。
- Provider 不可用时按设计显式降级，并在 Brief/SSE 中展示 `source_status`。
- 日志不得包含完整私人全文、完整查询或凭据；测试必须验证脱敏。

### 6.4 检索、Agent 与证据

- 所有候选结果先应用 workspace、scope、生命周期和版本过滤。
- `personal_fulltext > structured_abstract > web_context` 的排序与资格规则必须有测试。
- `metadata_only` 不得进入 Evidence；`web_context` 不得单独形成科学结论。
- Agent 保持有界状态机：最多 8 个工具步骤、120 秒软超时，不允许自由循环。
- SSE 和 Brief 只展示计划、阶段、工具、来源、降级和结果，不展示隐藏推理。
- 检索策略、rerank、chunk 参数变化必须伴随质量回归和 ADR/设计更新。

### 6.5 Web

- 页面必须显式展示同步覆盖、数据陈旧、来源降级和错误恢复状态。
- 关键交互使用组件测试；完整用户旅程使用 Playwright。
- 不以 UI 隐藏错误代替服务端降级语义。
- 不在浏览器保存 Zotero Key、模型 Key 或任何长期 Provider 凭据。
- 关键页面至少覆盖键盘操作、焦点可见性和基础可访问姓名/标签。

## 7. 安全、隐私与数据规则

- 仓库只能包含合成或脱敏 fixture；真实响应入库前必须移除个人信息、全文和凭据。
- `.env`、`config.local.yaml`、真实 Key、cookie 和日志不得进入 Git。
- 日志字段默认白名单；新增日志前判断是否包含问题原文、全文、DOI 之外的私人元数据。
- 所有多租户查询必须经过统一 Repository 或 domain filter，禁止 handler 直接 `db.Where`。
- 新增 API 必须包含未授权、越权和对象不存在三类测试。
- 删除、撤权、主动清空和 30 天清理必须有集成测试；备份不能绕过删除承诺。
- 依赖新增必须说明用途、许可证、维护状态和安全风险；能为标准库或现有依赖解决时不得引入新依赖。
- Agent 不得调用真实外部 Provider 来“证明功能可用”；需要真实调用时必须由用户明确授权，并使用本地忽略的凭据。

## 8. 验证命令与 CI 门禁

当前仓库尚未实现应用代码。阶段 0 必须建立以下稳定入口，后续开发只能通过仓库级命令验证：

| 命令 | 责任 |
|---|---|
| `make fmt-check` | Go/Web 格式检查 |
| `make lint` | 静态检查、类型检查和敏感信息扫描 |
| `make test-unit` | Go/Web 单元与组件测试 |
| `make test-integration` | PostgreSQL/pgvector、Repository、迁移和并发集成测试 |
| `make test-contract` | Zotero、Provider、OpenAPI 和 API 合同测试 |
| `make test-e2e` | 本地 stub 环境 Playwright 主流程 |
| `make openapi-lint` | OpenAPI 3.1 校验 |
| `make smoke-stage0` | 阶段 0 端到端 smoke test |
| `make verify` | 聚合上述默认离线门禁 |

规则：

- 阶段 0 完成前，可以记录尚未存在的目标命令，但不得声称其通过。
- 阶段 0 完成后，新增功能 PR 必须运行 `make verify`；大型测试可按 CI 分层，但合并门禁结果必须等价。
- 真实 Zotero、S2、OpenAlex、Qwen 调用不进入默认 CI；用 fixture/stub 验证。
- CI 必须至少包含：格式、lint、单元、集成、合同、OpenAPI、Web 构建、E2E、密钥扫描和迁移验证。
- 失败测试不得跳过。确认为 flaky 时必须先记录根因、修复并保留回归测试；无法快速修复时不得合并依赖该测试的变更。
- 文档-only 变更不运行应用测试，但必须执行 Markdown 链接检查、YAML/JSON 解析和 `git diff --check`。

## 9. Definition of Done

一个 Change Spec 只有同时满足以下条件才能进入 `Done`：

- [ ] 规格状态为 `Verifying`，范围、非目标、风险和决策记录完整。
- [ ] 所有 `AC-xxx` 有对应测试，并实际通过。
- [ ] 每个新行为有 Red 证据、Green 证据和必要重构后的复跑证据。
- [ ] 受影响模块测试、数据库集成测试、合同测试和仓库级验证通过。
- [ ] 产品/架构/设计/OpenAPI/migration 中受影响的文档已更新且链接有效。
- [ ] workspace 隔离、权限、删除生命周期和日志脱敏已验证。
- [ ] Provider 限流、超时、降级和错误映射已验证。
- [ ] 用户可见错误、来源状态和覆盖缺口没有被静默吞掉。
- [ ] 没有真实密钥、私人全文、PDF、生产数据或超范围日志。
- [ ] `git diff --check` 通过；没有无关生成物或调试文件。
- [ ] 已说明回滚方式或为什么无需迁移回滚。
- [ ] PR 或交付记录包含规格 ID、测试命令、结果、已知限制和未覆盖风险。

文档-only 变更的 DoD 是：链接可解析、术语与上游一致、无未决冲突、差异检查通过，并明确没有运行应用测试的原因。

## 10. PR、评审与 Agent 交付格式

### 10.1 PR 或合并请求最小内容

```text
Spec: RS-SPEC-xxxx
Outcome:
AC covered: AC-001, AC-002
Test evidence:
  - Red:
  - Green:
  - Full verification:
Contract/docs changed:
Migration/rollback:
Security/privacy:
Known limitations:
```

### 10.2 评审顺序

1. 规格是否完整，是否改变了上游事实源。
2. 验收条件是否覆盖成功、边界和异常路径。
3. 测试是否先失败、后通过，是否真正断言行为。
4. 租户隔离、隐私、删除、Provider 降级和错误处理。
5. 数据迁移、幂等、并发和回滚。
6. 代码结构与依赖方向是否符合设计。
7. 文档、OpenAPI、migration 和可观测性是否同步。
8. 是否引入无关范围、未授权依赖或调试残留。

### 10.3 Agent 强制行为

编码 Agent 在修改仓库前必须：

1. 阅读 `AGENTS.md`、`CLAUDE.md`、相关 PRD、架构、设计、OpenAPI 和本规范。
2. 找到现有 Change Spec；不存在时先创建并完成 Ready 门禁。
3. 明确本次只处理哪个规格、哪些 `AC-xxx`、哪些文件范围。
4. 先写测试并运行到失败，再修改生产代码。
5. 不修改用户未要求的产品结论、历史评测结果或冻结架构。
6. 不自动 commit、push、创建 PR 或发布；仅在用户明确要求时执行。
7. 完成后报告：规格 ID、实现结果、AC 映射、Red/Green 证据、完整验证命令、风险与限制。
8. 如果无法运行某验证，必须说明原因、未验证范围和替代检查；不得声称未运行的命令通过。

## 11. 缺陷、Spike 与紧急修复

### 11.1 缺陷修复

1. 先写能稳定复现缺陷的测试，确认在当前版本失败。
2. 判断是回归、规格缺口还是上游合同变化。
3. 回归问题增加长期保护测试；规格缺口先更新规格。
4. 只做最小有效修复，不顺手重构无关模块。
5. 运行受影响测试和完整回归；若用户可见行为变化，更新 PRD 或发布说明。

### 11.2 Spike

- Spike 必须写明时间盒、问题、成功信号和退出方式。
- Spike 分支或目录不得成为生产实现。
- 结论沉淀到 ADR/设计或 Change Spec，生产实现重新走 TDD。
- 未被验收的 Spike 代码不得用“已经写好了”作为跳过规格的理由。

### 11.3 紧急修复

- 允许先回滚或最小修复以恢复服务。
- 必须保留事故时间线、影响范围和临时措施。
- 同一工作日必须补复现测试；无法当日完成时必须有明确负责人和截止时间。
- 不得把紧急修复当作永久绕过测试、权限或迁移规范的理由。

## 12. 规范生效与修订

- 本规范自 `v1.0` 起立即生效，优先约束阶段 0 及之后所有实现。
- 阶段 0 的第一个 Change Spec 必须是 `stage0-smoke-test`，并建立本规范要求的验证命令和 CI 骨架。
- 本规范不得被模块文档或临时实现覆盖；发生冲突时先修订 PRD/ADR/设计/本规范，再继续编码。
- 修订本规范时必须同步检查 `AGENTS.md` 和 `CLAUDE.md`，保证 Agent 约束指针与正文一致。
- 规范版本提升应说明变化、生效日期、受影响工作和迁移要求。

## 附录 B：验收条件写法

有效：

```text
AC-003：Given 一个 workspace 拥有 collection A 和 collection B，
When 查询只授权 scope A，
Then 返回的 Evidence 与引用均不得包含 collection B 的文档或 chunk。
```

无效：

```text
AC-003：scope 要正确。
```

每个异常路径至少考虑：

- 输入非法、缺失或超限。
- 未授权、越权或对象不存在。
- 上游超时、限流、返回非法数据或能力缺失。
- 重复请求、并发请求、重复同步和断线重连。
- 数据被删除、版本过期或 scope 变化。
- 部分成功、部分降级和来源状态变化。
