# ADR-016：阶段 1 保持 pgx 数据访问与同步型任务边界

| 项目 | 内容 |
|---|---|
| 状态 | 已采用 |
| 日期 | 2026-10-17 |
| 影响范围 | 数据访问、迁移、后台任务运行时 |
| 关联 | ADR-003、ADR-004、RS-SPEC-0002 |

## 决策

阶段 1 保持阶段 0 已验证的 `pgx + 文件名顺序迁移 runner`，不引入 GORM/Goose 双轨。同步任务在本切片以可重入的 worker 命令执行，所有状态和游标持久化在 PostgreSQL；任务边界必须允许后续替换为 River，不得把任务状态放在进程内存。

River 运行时接入和任务恢复/重试调度在后续生命周期切片完成。阶段 1 的验收只要求“可重复运行、断点状态不丢失、失败保留旧 active epoch”，不宣称 River runtime 已实现。

## 原因

- 阶段 0 已有可运行、幂等、经过集成验证的 pgx 实现；切换 ORM 和迁移器会扩大本切片风险，却不改善同步语义。
- 阶段 1 的主要不确定性在 Zotero HTTP、凭据加密、版本/删除和原子 epoch 发布，应先验证这些边界。
- 保持 PostgreSQL 为唯一状态核心，不引入 Redis/Kafka；后续可以按同一 job 边界接入 River。

## 后果

- 架构基线中的 GORM/Goose/River 仍是目标方向，但阶段 1 实现事实以本 ADR 为准。
- 任何需要进程崩溃后自动重跑的任务，必须在后续 River 切片完成；当前 CLI 运行失败时保留可续跑游标和旧 active epoch。
- 新增实现不得在内存中保存唯一任务状态，不得在 API 请求中同步执行长任务。
