## 1. 决策摘要

### 1.1 一句话定义

Research Scout 是一个面向课题组研究者的文献调研助手：以用户个人 Zotero 文库中的可用全文和元数据为个人证据，结合 Semantic Scholar、OpenAlex 与模型供应商原生联网搜索，在显式的检索范围和证据层级内回答问题、发现缺口并生成可核验的研究简报。

### 1.2 背景

原项目已经验证了“查询改写 → 混合检索 → 重排 → 带引用综合”的技术链路，并建立过一个包含 26 个 venue、57,343 篇论文的中央摘要库。该库证明了垂直检索和生成的可行性，也暴露了三个无法靠继续扩大开发者维护语料库来解决的问题：

1. 摘要无法支撑方法、实验、公式、表格等全文级研究问题。
2. 开发者无法合法、稳定、低成本地获取全领域全文，也无法承诺覆盖完整。
3. 用户真正关心的是“我的文献库里有什么”和“我漏掉了什么”，而不是一个与个人阅读状态脱节的公共摘要索引。

因此，新产品把个人语料的维护责任交还给文献所有者：Zotero 是用户原文和 collection 的事实源。系统通过 Zotero Web API 读取用户已同步的个人文库并建立服务端派生索引；对 Web API 可见但没有 fulltext 的条目标记摘要级或仅元数据，对本地-only/未同步内容则明确提示“可能未覆盖”，但不声称可以枚举这些本地条目。

原有 57,343 篇中央摘要库及其向量数据已于 2026-10-16 删除。旧代码只保留作历史参考，不作为新产品的数据迁移来源。

### 1.3 已确认决策

| 决策项 | 结论 |
|---|---|
| 产品定位 | 课题组研究基础设施，不是毕业研究原型或个人文献管理器 |
| 首要场景 | 个人 Zotero 文库问答 + 库外缺口发现 + 可核验研究简报 |
| v1 Zotero 接入 | 仅使用 Zotero Web API，读取个人 My Library |
| v1 Connector | 不开发、不安装、不进入验收；未来仅作为可选扩展 |
| Zotero 文库范围 | v1 仅个人 My Library，不支持 group libraries |
| 索引范围 | 连接后索引整个个人文库；研究项目查询时按 collection scope 过滤 |
| 同步方式 | 按需和手动刷新；使用 library version、`?since=` 和 deleted 数据做增量同步 |
| 原文存储 | 不保存 PDF、不解析 PDF、不提供 PDF 上传 |
| 全文/索引策略 | 有 Web API 可用 fulltext 时记为证据层 `personal_fulltext`；有摘要但无 fulltext 时记为证据层 `structured_abstract`；只有元数据时设为索引状态 `IndexStatus=metadata_only`，不进入证据层，也不伪装为摘要或全文 |
| 本地-only/未同步内容 | 显示“可能未覆盖”警告；Web API 无法枚举本地-only 条目，也不承诺覆盖用户所有本地 Zotero 资料 |
| 内容范围 | v1 只索引论文和标准元数据，不索引批注、高亮或私人笔记 |
| Zotero 关系 | 只读，不回写、不修改 collection、不删除条目 |
| 凭据处理 | 服务端加密保存并代理调用；浏览器不持久化 Zotero Key |
| 开发期认证 | 只读 Zotero API Key |
| 试点前认证 | 切换为 Zotero OAuth 1.0a；OAuth 2.0 不是当前 v1 前提 |
| 身份与 Lab Nexus | v1 独立开发，不接 Lab Nexus、不实现 OIDC；保留身份适配器边界 |
| 核心工作对象 | 研究项目；项目持续保存 scope、提问、简报和反馈 |
| 检索模式 | `my_library`、`gap_fill`、`landscape` 三档；Planner 只能建议，不能静默升级 |
| 结构化来源 | Semantic Scholar + OpenAlex；DBLP 延后 |
| 模型供应商原生联网搜索 | 仅在 `landscape` 模式启用；v1 首个 Provider 为 Qwen/DashScope，来源标记为低层级上下文 |
| 证据类型 | `personal_fulltext`、`structured_abstract`、`web_context` |
| 输出形式 | 完整研究简报 + 多轮追问 |
| 缺口展示 | 经典/权威、相关方法、最新进展三类并列 |
| 管理员审计 | 只有显式系统管理员可审计派生内容；教师不自动获得权限 |
| 私人历史 | 仅本人可见，可删除 |
| 分享协作 | v1 不做站内分享、研究卡片或公共库 |
| 数据生命周期 | Zotero 删除或撤权后立即退出检索，30 天后清除派生数据 |
| 模型边界 | 用户允许把命中片段交给配置的 LLM/Embedding API，首次使用明确告知 |
| 试点规模 | 3–5 名真实用户 |
| 原中央摘要库 | 数据库、向量和数据卷已删除；旧代码仅作历史参考 |

### 1.4 成功标准

试点以真实任务验证为主：

- 3–5 名用户各完成至少 3 个真实研究问题。
- 没有安装 Zotero 或没有连接个人文库的用户，仍可完成外部发现与全景调研。
- 已连接 Zotero Web API 的用户，能够完成同步、查看覆盖状态并基于个人证据提问。
- 70% 的调研任务被用户评价为“对实际问题有帮助”。
- 80% 的研究简报包含可核验、可追溯的引用。
- 至少产生一次“发现库外论文并自行收藏到 Zotero”的真实事件。
- 用户能够理解哪些内容已索引、哪些是全文级或摘要级证据、哪些仅元数据、哪些属于本地-only 或 fulltext 缺失。

### 1.5 非目标

- 不在 v1 开发 macOS、Windows 或 Linux Connector。
- 不抓取、不维护、不扩张开发者控制的中央全文或摘要语料库。
- 不保存原始 PDF，不解析 PDF，不成为第二个 Zotero 或 EndNote。
- 不修改 Zotero 条目、collection、附件、标签或阅读状态。
- v1 不索引 Zotero 批注、高亮、笔记或私人研究想法。
- v1 不支持 group libraries。
- v1 不做手动 PDF 上传。
- v1 不做站内分享、研究卡片、公共投稿与公共精选库。
- 不承诺覆盖整个信息安全领域，也不承诺穷尽整个互联网。
- 不诊断用户属于哪个年级或角色，学生与教师使用同一套功能。
- 不向用户展示模型隐藏推理，只展示调研计划、工具、来源和证据。

## 2. 目标、原则与用户

### 2.1 产品目标

1. 让用户能基于个人 Zotero 文库中可获得的全文或摘要回答问题，并明确知道证据层级。
2. 让用户能在个人文库之外发现经典工作、相关方法和最新进展，形成真实的研究缺口。
3. 让外部检索、联网背景和模型生成都在显式范围与来源规则内运行。
4. 让每条关键结论都可以回到论文、Zotero 条目、DOI、URL 或证据片段。
5. 让用户能够控制连接、同步、清空、删除和审计边界，不必维护第二套文献管理器。
- 先验证个人文库与外部发现的组合价值，再决定是否增加 Connector、本地模型和其他入口。

### 2.2 产品原则

- **个人证据优先**：能取得个人全文时优先使用；只有摘要时明确降级，不伪装全文。
- **范围显式**：用户选择的模式、项目 scope 和实际来源必须在界面上可见。
- **缺口诚实**：本地-only、未同步、无 fulltext、限流和搜索失败都要显示，不包装成“没有结果”。
- **结构可追溯**：结论、证据、引用和原始来源保持稳定关系，历史简报不能被新同步静默改写。
- **只读与最小权限**：产品不修改 Zotero，不获取不必要的写权限，不保存 PDF。
- **来源分层**：个人全文、结构化摘要和联网上下文不混为一谈。
- **可替换供应商**：S2、OpenAlex、搜索、LLM 和 embedding 都通过适配器接入。
- **有界执行**：Agent 有明确步骤、工具权限、预算和终止条件。
- **不做中央语料库**：开发者不维护新的公共论文库；个人文库责任归还用户。

### 2.3 用户与权限角色

学生与教师使用同一能力模型。角色不决定检索能力，只决定是否存在显式系统管理权限。

| 角色 | 能力 |
|---|---|
| 普通用户 | 管理自己的连接、项目、scope、查询、简报、历史和删除操作 |
| 显式系统管理员 | 普通用户能力之外，可按审计流程查看派生内容和管理系统状态 |
| 未来身份提供方 | 通过身份适配器提供 `actor_id`、`workspace_id` 和角色，不是 v1 依赖 |

v1 不把 Lab Nexus 教师身份自动映射为管理员。管理员权限必须由本地显式配置或未来身份提供方的明确声明授予。

### 2.4 Jobs To Be Done

- 我想基于自己已经收集的文献快速回答一个具体问题。
- 我想跨多个 collection 综合一个主题，而不是逐篇打开 PDF。
- 我想知道自己的文库漏了哪些重要论文、方法或最新进展。
- 我想进入一个陌生领域，先获得可核验的入门地图，再决定读什么。
- 我想持续跟踪一个研究方向，并在后续提问中保留上下文。
- 我想把调研结果交给导师或同学讨论，且每条结论都能追溯来源。
- 我不想为了使用助手先维护一个新的文献管理器。
- 我想知道系统是否真的读到了全文，还是只看到了摘要或网页。

### 2.5 用户痛点与设计回应

| 痛点 | 设计回应 |
|---|---|
| “我收藏了很多，但真正读过的不多。” | 不要求先整理完 Zotero；连接后按整个文库建立索引 |
| “我不知道自己的库漏了什么。” | 外部检索与个人结果分层，单独展示三类缺口 |
| “AI 答案不知道从哪里来。” | 关键结论必须绑定引用和证据层级 |
| “全文获取困难、存储成本高、覆盖面不可控。” | 不集中保存 PDF，不由开发者预存全文 |
| “我的 Zotero 里还有本地-only 文件。” | 明确显示 Web API 覆盖范围和“可能未覆盖”警告，不虚假承诺全量 |
| “不想再维护一个文献管理器。” | 不做文献 CRUD，Zotero 继续作为事实源 |
| “我不确定联网搜索能不能信。” | `web_context` 不能单独支撑科学事实结论 |

## 3. 产品范围与信息架构

### 3.1 v1 范围

- 独立 workspace 与可替换身份适配器。
- Zotero Web API 连接、只读凭据管理、连接验证和撤权。
- 个人 My Library 全量元数据索引、可用 fulltext 读取和增量同步。
- collection 树、项目 scope 和多 collection 查询。
- 同步覆盖状态：全文级、摘要级、仅元数据、无 fulltext、删除待清理和失败。
- 研究项目管理、查询会话、私人历史和反馈。
- `my_library`、`gap_fill`、`landscape` 三种检索模式。
- Semantic Scholar + OpenAlex 外部发现和结果归一化。
- `landscape` 模式下的模型供应商原生联网搜索和低层级背景标注。
- 完整研究简报、三类缺口和多轮追问。
- 引用追溯、证据分层、外部结果只读与导出。
- 暂停同步、清空索引、删除项目和 30 天数据生命周期。
- 显式管理员审计和用户可见的审计记录。

### 3.2 v1 明确排除

| 排除项 | 原因 |
|---|---|
| macOS Connector | Local API 只存在于本机，先引入安装和同步链路会阻塞核心闭环 |
| Web API 之外的第二条 Zotero 接入路径 | v1 需要单一、可集中部署、可测试的事实源 |
| Group libraries | 权限、共享和审计模型不同，不能在个人文库 v1 中混用 |
| 站内分享和研究卡片 | 不是核心闭环，增加隐私和权限复杂度 |
| 公共精选库 | 需要独立的内容投稿、审核、版权和治理设计 |
| 手动 PDF 上传 | 会形成第二套原文摄入和存储责任 |
| PDF 解析与托管 | 与原文责任边界冲突；只处理 Web API 可取得的派生文本 |
| Zotero 写回 | 保持只读承诺，避免状态冲突 |
| Zotero 批注和笔记 | v1 不把私人阅读信号纳入产品范围 |
| 文献管理 CRUD | 继续由 Zotero 承担 |
| DBLP | 首版只解决核心发现需求，延后第三来源 |
| Windows/Linux Connector | 没有 v1 Connector，终点尚未定义 |
| 本地自托管模型 | v1 允许外部模型 API，本地模式作为后续增强 |

### 3.3 核心领域对象

| 对象 | 职责 |
|---|---|
| `ZoteroSource` | 统一 Zotero 来源边界；v1 只有 `WebAPISource` 实现 |
| `ZoteroConnection` | 用户连接、凭据状态、同步健康、最后刷新时间和覆盖摘要 |
| `LibrarySyncCursor` | library version、增量位置、失败状态和续跑信息 |
| `CollectionScope` | Zotero collection 集合；项目默认 scope 与单次查询 scope 分离 |
| `IndexedDocument` | item/attachment 标识、标准元数据、派生文本和索引状态 |
| `Chunk` | 文档分块、来源位置、版本和向量引用 |
| `Project` | 用户围绕一个研究主题持续工作的容器 |
| `QuerySession` | 一次包含模式、scope、过程、证据和追问的调研会话 |
| `ResearchBrief` | 一次调研的结构化输出 |
| `Evidence` | 证据层、引用位置、来源和可追溯链接 |
| `Gap` | 个人文库相对外部研究现状的缺口 |
| `AuditEvent` | 管理员访问或数据操作记录 |

固定枚举：

```text
RetrievalMode = my_library | gap_fill | landscape
EvidenceType = personal_fulltext | structured_abstract | web_context
GapType = canonical | related_method | latest_progress
IndexStatus = pending | indexed | metadata_only | failed | skipped
LifecycleStatus = active | removed_pending_purge | purged
```

### 3.4 信息架构

1. **工作台**：项目列表、最近调研、Zotero 连接状态、同步和待处理问题。
2. **Zotero 连接**：Web API 连接状态、文库覆盖、最后刷新、刷新和撤权。
3. **研究项目**：默认 scope、默认模式、历史会话、研究简报和反馈。
4. **提问页**：问题输入、模式选择、可选 collection scope 和调研预览。
5. **过程页**：计划、当前阶段、工具、来源和降级状态；不展示隐藏推理。
6. **简报页**：结论摘要、证据化发现、方法与时间脉络、三类缺口、未决问题和引用。
7. **私人历史**：仅本人可见，可删除项目或单次会话。
8. **审计记录**：用户查看与自己相关的管理员访问记录。
9. **系统管理**：管理员角色、连接状态、租户配置和运行状态。

## 4. 核心用户旅程

### 4.1 首次使用：不连接 Zotero

1. 用户进入产品并创建研究项目。
2. 系统说明未连接个人文库时只能使用外部发现和联网背景。
3. 用户选择 `gap_fill` 或 `landscape`，输入研究问题。
4. 系统调用 S2/OpenAlex，必要时调用联网搜索。
5. 系统输出带来源分层的简报，并明确说明没有个人全文证据。

**完成标准**：用户不安装 Zotero 也能完成一次外部调研或全景扫描。

### 4.2 首次使用：连接 Zotero Web API

1. 用户打开“Zotero 连接”页面，阅读数据边界说明。
2. 开发期用户生成只读 Zotero API Key 并提交；正式试点使用 OAuth 1.0a。
3. 服务端验证连接并读取个人 My Library 和 collection 树。
4. 系统开始首次全量同步，展示进度、成功数量、摘要级数量和 fulltext 缺失数量。
5. 系统提示“Web API 只覆盖已同步到 zotero.org 的数据，本地-only 内容可能不在范围”。
6. 用户看到覆盖状态后创建或进入研究项目。

**完成标准**：用户连接成功，系统可以展示 Web API 可见文档、精确的 fulltext/摘要/元数据状态，以及本地-only 可能未覆盖的警告。

### 4.3 日常调研

1. 用户进入已有项目或创建新项目。
2. 系统默认带入项目 scope，但提问页始终显示本次实际范围。
3. 用户选择 `my_library`、`gap_fill` 或 `landscape`。
4. Planner 生成调研计划；若建议升级模式，必须先获得用户确认。
5. 系统执行检索并展示阶段、工具和来源。
6. 系统输出完整研究简报。
7. 用户继续追问或调整 scope 重新调研。

### 4.4 多轮追问

- 追问继承当前项目的 scope 和检索模式，但允许显式修改。
- 追问可以要求聚焦某篇论文、某个方法、某个证据或某个缺口。
- 新证据必须追加引用，不得覆盖此前引用的来源。
- 用户改变 scope 或模式时，系统明确标记本次回答使用了新的范围。
- 模型不确定或证据冲突时，展示冲突而不是强行给出单一结论。
- 历史简报保留生成时的 scope、来源和证据版本。

### 4.5 外部发现

1. 用户选择 `gap_fill` 或 `landscape`。
2. 系统检索个人文库，并调用 Semantic Scholar 或 OpenAlex。
3. 外部结果与个人结果按 DOI、稳定标识和标题/年份归一化去重。
4. 系统并列展示经典/权威、相关方法、最新进展三类缺口。
5. 用户查看 DOI、摘要、引用关系或外部页面。
6. 用户可复制 DOI/BibTeX 或跳转外部页面；系统不自动写回 Zotero。

### 4.6 同步失败与恢复

- Zotero API Key 无效或过期：要求重新授权，不继续同步。
- Zotero Web API 限流：按 `Retry-After` 退避，显示来源暂不可用。
- 网络中断：增量同步可续跑，重复执行不产生重复文档或向量。
- 单篇 item/fulltext 请求失败：记录条目状态并按需重试，不阻断整个文库。
- fulltext 缺失或为空：按摘要级或仅元数据正常降级，不视为同步失败。
- 用户撤权或断开连接：立即停止新同步，文档退出检索，进入清理流程。

## 5. 功能需求

以下功能均为 P0。每项需求必须同时满足业务规则、异常规则和验收条件。

### FR-01 独立身份、Workspace 与租户隔离

**用户故事**：作为用户，我希望只访问自己的工作区和数据，不依赖尚未稳定的外部登录系统。

**业务规则**

- v1 使用可替换的身份适配器，不接 Lab Nexus、不实现 OIDC。
- 每个用户至少绑定一个 `workspace_id`，所有个人数据在该边界内存储和检索。
- 服务端从已认证上下文注入 `actor_id` 和 `workspace_id`，不信任前端传值。
- 角色只区分普通用户和显式系统管理员，不从教师/学生身份推断。
- 未来接入 Lab Nexus 或其他 IdP 时，只替换适配器，不改变领域对象。

**异常路径**

- 身份适配器不可用时拒绝新登录；已有会话按安全策略处理。
- 角色解析失败时采用最小权限，不得自动提升为管理员。

**验收条件**

- 两个 workspace 的用户互相访问项目或文档 API 时均被拒绝。
- 教师账号未显式授予管理员时无法审计他人文库。
- 替换身份适配器不需要修改项目、证据或生命周期业务逻辑。

### FR-02 Zotero Web API 连接与凭据

**用户故事**：作为 Zotero 用户，我希望用只读授权连接个人文库，并清楚知道系统能读取什么。

**业务规则**

- v1 唯一接入方式是 Zotero Web API，个人 My Library。
- 开发期支持只读 API Key；正式试点前切换 Zotero OAuth 1.0a。
- 凭据只由服务端加密保存，浏览器不持久化 Key。
- 服务端使用官方 Web API 基址、API 版本和分页规范调用。
- 连接页面明确说明：题录同步不等于 PDF/fulltext 一定同步；本地-only 内容可能不在范围内。
- 用户可以验证连接、刷新、暂停和断开连接。

**异常路径**

- Key 或授权失效时停止同步并引导重新授权。
- API 版本不兼容时显示最低要求和修复步骤。
- 429、网络超时和服务端错误进入有限重试与退避。

**验收条件**

- 凭据不会出现在浏览器存储、前端 bundle 或普通日志中。
- 断开连接后，服务端不再调用 Zotero Web API。
- 用户可以查看连接状态、最后同步时间和覆盖摘要。

### FR-03 个人文库全量索引与增量同步

**用户故事**：作为用户，我希望连接后一次建立文库索引，后续只同步变化内容。

**业务规则**

- 连接后索引整个个人 My Library，不在连接时要求用户先选 collection。
- 首次同步读取 item、attachment、collection 关系和可用 fulltext。
- 后续同步使用 library version、`?since=`、`format=versions` 和 deleted 数据。
- 同步必须幂等，不能因为重复运行产生重复文档、chunk 或向量。
- 并发不超过 4，遵守 429、`Retry-After` 和指数退避。
- 单篇失败不阻断整个文库，失败清单可重试或跳过。
- 全文缺失不阻断元数据同步和摘要级检索。

**异常路径**

- collection 重命名或移动时使用稳定标识，不使用名称作为主键。
- 条目被删除时建立 tombstone，立即退出检索。
- 用户撤权或断开连接时停止同步并启动生命周期处理。

**验收条件**

- 连续运行两次同步，文档、chunk 和向量数量不增加重复行。
- 中断后重新同步只补齐未完成内容。
- Web API 返回删除后，下一个同步周期内文档不再进入检索。

### FR-04 元数据、全文与索引状态

**用户故事**：作为用户，我希望系统区分全文证据、摘要证据和仅有元数据的索引状态，不要让我误判证据强度。

**业务规则**

- 每条规范化论文保留标题、作者、年份、venue、DOI、Zotero item/attachment 标识和来源。
- Web API 可取 fulltext 时建立 `personal_fulltext` 文档。
- 有摘要但无 fulltext 时建立 `structured_abstract` 证据；只有元数据时仅设置 `IndexStatus=metadata_only`，不伪装为摘要或全文。
- `metadata_only` 是索引状态，不是 `EvidenceType`；它不能独立支撑科学结论。
- `structured_abstract` 只能引用来源实际返回的摘要文本，不能由标题或元数据推断生成。
- 同一论文以 DOI 优先，其次稳定学术标识，最后标题与年份归一化去重。
- chunk 保留论文内来源位置；位置不可可靠获取时至少保留文档级追溯。

**异常路径**

- 无可用 fulltext 时按正常缺省降级为摘要或仅元数据，不标记为同步失败；只有请求本身或响应结构出现可重试错误时才标记 `failed`，且不得阻断元数据同步。
- 同一论文出现在多个 collection 时只保留一个文档实体和多条 scope 关系。
- 文档版本更新时建立新版本，避免旧引用指向未发布内容。

**验收条件**

- 界面能够区分全文级、摘要级和仅元数据索引状态。
- `metadata_only` 条目不会进入科学结论证据列表，只能用于覆盖状态、引用定位或提示缺口。
- 方法或实验问题能命中正文 chunk，而不仅是标题或摘要。
- 摘要级回答明确标注“不含全文”，不产生全文级确定性措辞。

### FR-05 覆盖状态与本地-only 缺口提示

**用户故事**：作为用户，我希望知道系统是否真的覆盖了我的文库、哪些内容没有被读取，以及哪些状态无法通过 Web API 确认。

**业务规则**

- 按连接展示条目数、已索引数、全文级数、摘要级数、仅元数据数、失败数和最后刷新时间。
- 对 Web API 可见但无 fulltext 的条目给出可计数缺口；对本地-only/未同步内容只展示“可能未覆盖”的覆盖警告。
- Web API 无法枚举本地-only 条目，因此系统不得为这类内容显示精确条目数或声称已知其内容。
- 覆盖状态只描述当前 Web API 可见范围，不承诺覆盖用户所有本地资料。
- 状态未知时显示“未知”，不得用 0 或已完成代替。
- 部分同步完成时展示部分成功，不把整体标记为成功或失败。

**异常路径**

- 同步进行中时展示当前阶段和已完成数量。
- 失败条目必须能定位并触发重试或跳过。
- 断开连接后显示“已断开”和最后有效覆盖状态，不继续声称数据最新。

**验收条件**

- 用户可以一眼看出“全文级、摘要级、仅元数据、未覆盖”的差异。
- 系统不会把“本地-only/未同步”显示为已枚举条目或精确数量，但会明确提示可能存在未覆盖内容。
- 覆盖状态与实际可检索数量一致。

### FR-06 研究项目管理

**用户故事**：作为研究者，我希望围绕一个研究主题持续提问和积累简报。

**业务规则**

- 用户可以创建、重命名、归档和删除项目。
- 项目保存默认 collection scope、默认检索模式和历次会话。
- 项目不复制文献，不形成独立文献库。
- 项目历史默认仅本人可见。
- 项目可以包含多轮查询、简报和用户反馈。

**异常路径**

- 项目引用的 collection 在 Zotero 中删除或从 Web API 可见范围消失后，项目标记 scope 失效并要求重选。
- 项目删除后立即从产品列表消失，后台按生命周期规则清理。

**验收条件**

- 同一项目连续进行多轮调研，历史引用不丢失。
- collection 失效后不能继续使用旧 scope 静默查询。
- 另一个 workspace 的用户无法通过链接或接口访问项目。

### FR-07 Collection Scope 查询过滤

**用户故事**：作为用户，我希望在已索引文库中选择一个或多个 collection 进行本次调研。

**业务规则**

- 系统索引整个个人 My Library；查询时可以选择一个或多个 collection。
- 项目可以设置默认 scope，但提问页必须显示本次实际 scope。
- 用户可以不选 collection，使用整个个人文库作为查询范围。
- 未授权、已删除或同步失败的 collection 不能静默参与检索。
- scope 只改变检索过滤，不复制文档、不重新建立个人文库，也不因从项目 scope 移除而删除索引。

**异常路径**

- scope 中部分 collection 失效时，提交前要求用户确认或移除。
- 新输入范围与项目默认范围不同时，在简报中记录实际范围。
- 未连接 Zotero 时禁用个人文库范围，并清晰说明可用模式。

**验收条件**

- 多选 collection 的查询能命中各 collection 中的相关文档。
- 修改项目默认 scope 不改变历史简报记录的范围。
- 保存的 scope 可以复用、编辑和删除。

### FR-08 三种检索模式

**用户故事**：作为用户，我希望根据任务选择只查个人文库、查缺补漏或做全景调研。

**业务规则**

| 模式 | 个人文库 | S2/OpenAlex | 联网搜索 | 主要用途 |
|---|:---:|:---:|:---:|---|
| `my_library` | ✓ |  |  | 个人材料问答、跨 collection 综合 |
| `gap_fill` | ✓（若连接） | ✓ |  | 发现经典工作、相关方法和最新进展 |
| `landscape` | ✓（若连接） | ✓ | ✓ | 陌生主题、背景和行业现状扫描 |

- 每次提问前显式选择模式。
- Planner 可以建议切换模式，但必须由用户确认。
- 未连接 Zotero 时，`my_library` 禁用；`gap_fill` 和 `landscape` 仍可使用外部来源。
- 外部来源失败时不得降低个人文库结果的可信度。
- 简报必须记录实际使用的模式、scope 和来源状态。

**验收条件**

- `my_library` 模式不发出外部学术或联网搜索请求。
- `gap_fill` 模式不调用模型供应商原生联网搜索。
- `landscape` 模式对联网来源做低层级证据标注。
- Planner 建议升级后未确认时，系统仍执行原模式。

### FR-09 结构化外部发现

**用户故事**：作为用户，我希望借助 Semantic Scholar 和 OpenAlex 找到个人文库遗漏的重要论文。

**业务规则**

- Semantic Scholar 负责语义发现、引用关系和论文标识。
- OpenAlex 负责元数据、摘要、DOI 和来源补充。
- 外部结果必须归一化后再与个人文库去重。
- 每个结果展示来源、年份、venue、DOI 和可追溯链接。
- DBLP、Crossref 和其他来源不在 v1 产品承诺内，但接口允许后续增加适配器。

**异常路径**

- S2 或 OpenAlex 限流时展示结构化来源暂不可用，并允许稍后重试。
- OpenAlex 缺少摘要时保留元数据，不伪造摘要。
- 外部结果冲突时同时展示来源并标记冲突，不静默选择。

**验收条件**

- 同一 DOI 在 S2、OpenAlex 和个人文库中只出现一个规范化论文实体。
- 任一外部来源失败时，其他来源和个人文库结果仍可展示。
- 外部结果不会进入个人全文证据层。

### FR-10 模型供应商原生联网搜索

**用户故事**：作为用户，我希望在全景调研时补充网页背景，但能清楚区分网页内容和论文证据。

**业务规则**

- 仅在 `landscape` 模式启用。
- v1 首个 Provider 为 Qwen/DashScope；Provider 不支持原生搜索时返回明确的不可用状态，不静默伪造覆盖。
- 搜索结果必须包含可访问来源链接和抓取时间。
- 网页内容标记为 `web_context`，不能单独支撑科学事实结论。
- 不把整页网页永久保存为语料；只保留实现引用所需的摘要、链接和元数据。
- 用户问题可能发送给外部搜索和模型服务，首次使用时明确告知。

**异常路径**

- 搜索供应商不可用时标记该层降级，不阻断个人文库与结构化来源。
- 网页内容与论文结论冲突时优先展示论文证据并注明冲突。
- 未配置搜索供应商时，`my_library` 和 `gap_fill` 完全可用。

**验收条件**

- 联网来源在简报中具有独立标签和链接。
- 删除会话后，非必要网页上下文按生命周期规则清除。
- 仅引用网页背景时不能生成无保留的科学事实结论。

### FR-11 完整研究简报

**用户故事**：作为用户，我希望得到一份能直接用于调研讨论的结构化简报。

**业务规则**

默认固定包含：

1. 结论摘要。
2. 按主题组织的证据化发现。
3. 方法分类与时间脉络。
4. 三类缺口：经典/权威工作、相关方法、最新进展。
5. 当前证据无法回答的问题。
6. 引用与证据列表。

- 每条关键结论必须绑定至少一个引用锚点。
- 个人全文、结构化摘要、联网上下文必须分层标注。
- 证据不足时明确说明，不使用确定性语言补全。
- 简报保留本次 scope、模式、来源、证据版本和生成时间。

**验收条件**

- 随机抽样关键结论可追溯到具体文档、chunk 或来源。
- 取下任一关键引用后，对应结论应被标记为证据不足，而不是保持原样。
- 简报能够显示三类缺口，且不把“未找到”误写成“领域不存在”。

### FR-12 多轮追问

**用户故事**：作为用户，我希望继续追问某篇论文、某类方法或某个缺口，而不必重新描述背景。

**业务规则**

- 追问继承当前项目的 scope 和模式，但界面显示继承状态。
- 用户可以显式修改 scope 或模式。
- 新证据追加到证据列表，不覆盖历史来源。
- 追问可以引用已有结论、论文、证据或缺口作为上下文。
- 用户改变范围后，简报明确标记“本次使用了新的检索范围”。

**验收条件**

- 连续 3 轮追问后，原始引用仍可访问。
- 修改 scope 后，系统不会把旧范围结果误标为新范围结果。
- 追问不能访问用户未授权的 collection。

### FR-13 证据分层与引用追溯

**用户故事**：作为用户，我希望知道一条结论究竟来自我的全文、外部摘要，还是网页背景。

**业务规则**

| 证据层 | 类型 | 可作为科学结论依据 |
|---|---|---|
| 个人全文 | `personal_fulltext` | 是，最高优先级 |
| 结构化摘要 | `structured_abstract` | 是，但必须标注限于摘要 |
| 联网上下文 | `web_context` | 否，只能提供背景或线索 |

- 引用应包含论文标题、来源、年份、DOI/URL 和可用文档内定位。
- 定位信息不稳定时，至少追溯到论文级。
- 引用冲突时展示不同来源和冲突点。
- 用户点击引用可回到 Zotero item、DOI 或外部页面。

**验收条件**

- 只依赖联网上下文时不能生成无保留的科学事实结论。
- 结构化摘要与个人全文冲突时，系统提示冲突并显示两者。
- 引用链接失效时保留规范标识和最后验证时间。

### FR-14 外部结果只读与导出

**用户故事**：作为用户，我希望把发现的论文带回自己的研究工作流，但不让系统擅自修改 Zotero。

**业务规则**

- 外部结果支持复制 DOI、复制 BibTeX、打开出版商页面和打开 Zotero。
- 系统不自动写入 Zotero，不创建 collection，不下载并托管 PDF。
- 用户可以手动把论文加入 Zotero；待其同步到 Zotero Web library 后，下一次 Web API 同步才会进入个人文库。
- 导出只使用规范化元数据，不包含服务端派生的私人全文。

**异常路径**

- DOI 或链接无效时显示原始来源记录和最后验证时间。
- 用户未安装 Zotero 时提供 DOI/BibTeX 导出，不阻断结果查看。

**验收条件**

- 产品界面不存在自动写回 Zotero 的入口。
- 复制出的 DOI/BibTeX 可被 Zotero 正常导入。
- 外部结果不会改变个人库 scope 或索引。

### FR-15 私人历史与反馈

**用户故事**：作为用户，我希望回看自己的检索、简报和反馈，并控制它们的可见性。

**业务规则**

- 项目、会话、简报和反馈默认仅本人可见。
- 用户可以重命名、归档、删除会话和项目。
- 用户可以标记“有帮助”“不准确”“引用有问题”等反馈。
- 反馈用于评测和改进，不公开展示用户身份或私人全文。
- 删除后立即从产品历史中移除，后台按生命周期规则清理。

**异常路径**

- 反馈提交失败时保存草稿或提示重试，不静默丢失。
- 删除进行中显示状态，刷新后仍可看到清理进度。

**验收条件**

- 其他普通用户无法读取本人历史或反馈。
- 删除后的历史不会出现在检索、导出或项目列表。
- 用户可以查看会话使用的 scope、模式和证据层。

### FR-16 删除、清空与数据生命周期

**用户故事**：作为用户，我希望随时撤销授权、清空索引和删除数据，并知道何时彻底清除。

**业务规则**

| 事件 | 活跃索引 | 派生数据保留 | 最终清理 |
|---|---|---|---|
| Zotero 删除条目 | 立即移除 | 30 天回收期 | 30 天后清除 |
| 撤销连接 | 立即停止同步并移出检索 | 30 天回收期 | 30 天后清除 |
| 项目/查询 scope 调整 | 立即改变后续查询过滤 | 不清除个人文库索引 | 历史简报保留原 scope |
| 用户主动清空索引 | 立即清空 | 不保留回收期 | 确认后立即清除 |
| 删除项目或会话 | 立即不可见 | 30 天回收期 | 30 天后清除 |
| 删除账户 | 立即撤销会话 | 30 天回收期 | 30 天内清除全部派生数据 |

- 清理范围包括派生全文、chunk、向量、scope 关系和查询关联。
- 清理不删除用户 Zotero 中的任何内容。
- 用户必须在清空索引前看到影响范围和不可逆提示。

**验收条件**

- Zotero 删除或撤权后的下一个同步周期，文档不再出现在检索结果中。
- 30 天后数据库中不存在对应派生文本和向量。
- 主动清空索引后立即无法通过任何历史接口恢复内容。
- 删除 Zotero 文档不会反向删除 Zotero 条目。

### FR-17 管理员审计

**用户故事**：作为系统管理员，我需要在安全事件或合规要求下审计派生内容，但权限必须明确且留痕。

**业务规则**

- 只有显式管理员可以进入审计功能。
- 审计范围包括用户、连接、collection、文档元数据、派生文本、查询和审计事件。
- 原始 PDF 不在服务端，因此管理员无法通过系统获取 PDF。
- 每次查看派生内容前必须重新认证，不能只依赖已登录的普通会话。
- 每次访问必须记录管理员、时间、对象、原因和请求标识。
- 用户可以查看与自己相关的管理员访问记录。
- 普通教师不能因为职称自动获得管理员权限。

**异常路径**

- 管理员重新认证失败、取消或超时：拒绝访问敏感内容，不延长普通用户会话。
- 审计日志写入失败时阻止敏感内容访问。

**验收条件**

- 普通用户和教师默认看不到审计入口。
- 每次管理员查看派生内容都会生成可见记录。
- 管理员未完成重新认证时无法访问派生内容。
- 撤销管理员角色后，访问被实时拒绝。

### FR-18 降级、重试与可观测性

**用户故事**：作为用户，我希望系统在部分依赖失败时继续可用，并明确告诉我缺了什么。

**业务规则**

- 个人文库检索不依赖外部搜索，外部来源失败时继续工作。
- 同步和外部检索必须支持有限重试、退避和断点续跑。
- 任何失败不得被包装为“没有结果”。
- 界面显示当前阶段、完成的来源、跳过的来源和失败原因。
- 运行日志不得记录完整私人全文或个人查询原文，除非用户明确启用调试并知情同意。
- S2/OpenAlex 限流时显式降级，不静默漏答。

**验收条件**

- 切断 S2 后，`my_library` 模式仍能完整回答个人库问题。
- 切断网络后恢复同步时从断点继续。
- 外部来源失败时，简报显示“该来源不可用”，而不是零结果结论。
- 日志抽查不包含完整 PDF 文本或完整私人全文。

## 6. 检索、证据与回答规则

### 6.1 模式矩阵

| 能力 | `my_library` | `gap_fill` | `landscape` |
|---|:---:|:---:|:---:|
| 个人全文 RAG | ✓ | ✓（若连接） | ✓（若连接） |
| Semantic Scholar |  | ✓ | ✓ |
| OpenAlex |  | ✓ | ✓ |
| 模型供应商原生联网搜索 |  |  | ✓ |
| 缺口清单 |  | ✓ | ✓ |
| 方法与时间脉络 | ✓ | ✓ | ✓ |
| 联网背景 |  |  | ✓ |

### 6.2 检索编排

1. 解析用户问题，提取主题、时间、方法和比较意图。
2. 读取用户显式选择的模式、项目和 collection scope。
3. 强制应用 workspace、scope、tombstone 和文档版本过滤。
4. 在个人全文索引中执行混合检索和重排。
5. `gap_fill` 和 `landscape` 继续调用结构化来源。
6. `landscape` 在需要背景时调用联网搜索。
7. 去重、归一化、按证据层级重组候选集。
8. 判断证据是否足以支持结论；不足时生成未决问题和缺口。
9. 输出完整研究简报并记录来源与工具状态。

Planner 可以建议模式或补充 scope，但产品必须展示建议并要求用户确认。

### 6.3 缺口判定

三类缺口并列展示，不设置固定统一优先级：

- **经典/权威工作**：高引用、综述、领域共识或重要里程碑。
- **相关方法**：与问题相关但用户库未覆盖的方法、任务或应用场景。
- **最新进展**：用户库没有覆盖的近期论文、趋势或新问题。

每条缺口必须说明它相对哪个范围存在：缺失于个人文库、缺失于本次 collection scope、或仅由外部来源发现。不能把“当前检索未命中”直接表述为“领域不存在”。

### 6.4 引用与诚实性

- 关键结论必须引用证据。
- 引用必须支持该结论，不能仅做关键词相关。
- `personal_fulltext`、`structured_abstract` 和 `web_context` 是唯一证据层；`metadata_only` 只能帮助定位和展示缺口，不能作为科学结论证据。
- `personal_fulltext` 优先于 `structured_abstract`，`structured_abstract` 优先于 `web_context`。
- 联网上下文只能提供背景、术语或外部线索。
- 证据冲突、来源失效、摘要缺失和 fulltext 缺失必须显式展示。
- 不展示隐藏推理链，只展示可验证的计划、步骤、工具和证据。

## 7. 数据、权限与安全

### 7.1 数据清单

| 数据 | 所在位置 | 服务端是否保存 | 用途 |
|---|---|---:|---|
| 原始 PDF | 用户 Zotero | 否 | 原文事实源 |
| Zotero item/attachment 标识 | 服务端 | 是 | 同步、去重和追溯 |
| 标准论文元数据 | 服务端 | 是 | 检索、引用和展示 |
| Web API 可用 fulltext | 服务端 `text` | 是 | 个人全文检索 |
| 分块与向量 | 服务端 | 是 | 语义检索 |
| 查询与简报 | 服务端 | 是 | 项目历史和用户反馈 |
| 审计日志 | 服务端 | 是 | 管理员审计和安全追踪 |
| 原始网页 | 第三方或临时缓存 | 否，不长期保存 | 全景调研上下文 |

### 7.2 权限矩阵

| 操作 | 普通用户本人 | 其他普通用户 | 教师 | 显式管理员 |
|---|:---:|:---:|:---:|:---:|
| 管理自己的连接和项目 | ✓ |  | ✓ | ✓ |
| 查看自己的派生内容 | ✓ |  | ✓ | ✓ |
| 查看他人项目或历史 |  |  |  |  |
| 审计他人派生内容 |  |  |  | ✓ |
| 获取原始 PDF | 用户自己的 Zotero |  |  |  |
| 修改 Zotero |  |  |  |  |

### 7.3 隐私与信任承诺

首次连接或首次外部调研时，界面必须使用不含糊的语言说明：

> 本服务不会上传或保存你的原始 PDF，也不会修改 Zotero。为了提供检索和问答，服务端会保存通过 Zotero Web API 获得的元数据和可用派生文本、分块、向量。Web API 只覆盖已同步到 zotero.org 的内容，本地-only 资料可能不在范围内。命中片段可能发送给配置的 LLM/Embedding 或搜索服务。个人文库不是端到端私密空间，显式系统管理员可以审计派生内容；管理员访问会留下记录，你可以在产品内查看。你可以随时暂停同步、清空索引或删除账户。

### 7.4 安全要求

- 所有公网通信使用 HTTPS。
- Zotero Key 或 OAuth token 只在服务端加密保存，不写入前端、日志或仓库。
- 服务端按 workspace 隔离存储和检索，所有访问在服务端鉴权。
- 管理员访问必须重新认证并记录审计事件。
- 敏感配置和 API 密钥不得写入仓库或前端。
- 日志、监控和分析事件不得包含完整私人全文。
- 删除操作必须在活跃索引、缓存、向量和查询历史中一致执行。

## 8. 非功能需求

### 8.1 平台与兼容性

- v1 只提供 Web 应用，支持常用现代浏览器的最新稳定版本。
- 当前开发阶段先完成本地集成验证；生产目标为单机 Linux + Docker Compose + Caddy，不要求 Kubernetes。
- 不要求用户安装桌面客户端即可使用外部发现和全景调研。
- Zotero 连接依赖用户的 Zotero Web API 数据和授权，不依赖 Local API。
- 如果未来增加 Connector，它必须作为独立交付物和 `ZoteroSource` 实现，不改变 v1 领域对象。
- Web API 版本、分页和限流行为必须通过合同测试覆盖。

### 8.2 可靠性

- 同步必须幂等、可恢复，不因服务重启丢失游标。
- 单篇文档失败不得阻断整个文库同步。
- 外部来源失败不得阻断个人文库查询。
- 关键任务必须记录脱敏结构化日志，支持定位失败阶段和对象。
- 任何自动重试必须有上限，并向用户展示当前状态。
- 429、`Retry-After` 和并发上限必须被显式实现，不能依赖无限重试。

### 8.3 体验与过程透明

- 用户提交问题后 1 秒内看到受理状态。
- 长任务至少每 5 秒更新一次阶段状态，或明确显示等待外部服务。
- 调研过程必须展示计划、阶段、工具和来源。
- 不展示不可验证的隐藏推理。
- 用户离开页面后重新进入，应能看到进行中或已完成的会话状态。

### 8.4 可维护性与扩展性

- 应用采用 Go 模块化单体（API + Worker）+ React/Vite Web 同仓交付，模块边界优先于微服务拆分。
- 服务端接口使用 OpenAPI 3.1 + REST，长任务进度使用 SSE；不展示隐藏推理。
- v1 使用单一 PostgreSQL/pgvector 数据核心和 PostgreSQL-backed 持久任务队列（首选 River），不引入独立向量库、Elasticsearch、Redis 或 Kafka，除非后续 ADR 明确批准。
- 外部学术来源和联网搜索通过适配器边界接入，避免业务逻辑绑定单一供应商。
- 新增来源不得改变证据分层和用户模式定义。
- 领域对象必须支持 workspace、用户、项目和来源隔离。
- 未来 Connector 必须实现同一 `ZoteroSource` 边界；批注/笔记和公共库属于独立扩展，必须先通过 ADR。
- 复杂 SQL 和向量查询必须封装在 repository 边界内，不泄漏到 Agent 层。

### 8.5 成本与容量

- 服务端只存储派生数据，容量按文本、分块和向量估算，不包含 PDF。
- 默认按需刷新，避免定时全量轮询和重复 embedding。
- 索引任务必须支持限流、并发控制和失败续跑。
- 外部模型和搜索调用必须可观测，避免无限重试造成成本失控。
- v1 不设置硬性响应时长目标，但必须避免依赖故障导致无限等待。

## 9. 指标、实验与验收

### 9.1 试点指标

| 指标 | 定义 | 目标 |
|---|---|---:|
| 试用人数 | 完成至少一次真实调研并提问的人数 | 3–5 |
| 真实任务数 | 每名用户完成的真实研究问题数 | 每人 ≥3 |
| 有用率 | 用户评价“对实际问题有帮助”的任务占比 | ≥70% |
| 引用可核验率 | 关键结论存在可打开、可追到来源的引用 | ≥80% |
| 库外发现事件 | 至少一次因系统发现而在 Zotero 收藏论文 | ≥1 |
| Zotero 连接成功率 | 发起连接后成功完成验证和至少一次索引 | ≥80% |
| 无 Zotero 外部调研 | 未连接 Zotero 的用户能完成外部发现与全景调研 | 100% |
| 覆盖状态准确性 | 展示索引数量与实际可检索数量一致 | 100% |
| 删除承诺 | 主动删除和 30 天清理符合生命周期表 | 100% |

### 9.2 追踪矩阵

| 用户目标 | 功能需求 | 验收场景 | 指标 |
|---|---|---|---|
| 基于个人证据答题 | FR-04、FR-08、FR-13 | 方法/实验问题命中全文或摘要层引用 | 有用率、引用可核验率 |
| 跨 collection 综合 | FR-07、FR-11 | 多选 scope 后命中各 collection | 任务完成率 |
| 连接并刷新文库 | FR-02、FR-03、FR-05 | Web API 连接、全量索引、增量刷新 | 连接成功率 |
| 控制个人数据 | FR-03、FR-16 | 撤权、清空索引、删除账户 | 删除承诺 |
| 发现库外缺口 | FR-08、FR-09、FR-11 | 仅外部来源检索也能形成缺口清单 | 库外发现事件 |
| 全景扫描 | FR-10、FR-11 | 联网内容被标记为低层级上下文 | 引用可核验率 |
| 权限与审计 | FR-01、FR-17 | 跨 workspace 拒绝、管理员访问留痕 | 审计完整性 |

### 9.3 验收用例

1. **无 Zotero 用户**：不连接个人文库，使用 `gap_fill` 和 `landscape` 完成一次调研。
2. **Web API 连接**：使用只读凭据连接，读取个人 My Library 和 collection 树。
3. **全量索引**：首次同步写入元数据、可用 fulltext、chunk 和向量。
4. **增量同步**：修改元数据、删除条目、撤权后分别验证更新、tombstone 和覆盖状态。
5. **fulltext 缺失**：无 fulltext 但有摘要的条目同步为证据层 `structured_abstract`；无摘要的条目设置为 `IndexStatus=metadata_only`。两者均不阻断文库。
6. **本地-only 提示**：系统显示“本地-only/未同步内容可能未覆盖”的警告，但不得声称枚举了本地-only 条目或给出精确数量。
7. **三种模式**：验证 `my_library` 不外呼，`gap_fill` 只调用结构化来源，`landscape` 才调用联网搜索。
8. **引用追溯**：从简报结论回到 Zotero item、DOI 或外部页面。
9. **生命周期**：撤权、清空索引和删除账户，验证活跃索引和 30 天清理。
10. **来源限流**：模拟 429，验证退避、状态提示和其他来源降级。
11. **租户隔离**：两个 workspace 普通用户互访被拒绝。
12. **审计**：管理员每次查看派生内容均需重新认证并生成用户可见记录；未完成认证的访问被拒绝，教师默认无权限。

## 10. 发布计划

### 10.1 阶段一：高保真原型

- 用内部账户验证 workspace 隔离和凭据安全。
- 完成 Zotero OAuth 1.0a 只读授权、撤权、重新授权和凭据清理验证，确保试点前完成切换。

- 每名用户完成至少 3 个真实问题。

### 10.4 阶段四：试点后生产部署

- 使用单机 Linux + Docker Compose + Caddy 完成 HTTPS 部署、备份、监控和告警。

- 公共精选库、Connector 和其他客户端继续作为后续路线，不阻塞生产 v1。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Zotero Web API 不含本地-only 内容和部分 fulltext | 用户认为覆盖不完整 | 覆盖状态和缺口提示；不承诺全部 Zotero 资料 |
| Zotero API 限流或版本变化 | 同步中断或字段不兼容 | 合同测试、退避、版本检测、失败续跑 |
| 开发期 API Key 管理不当 | 凭据泄露 | 服务端加密、前端不持久化、试点前 OAuth 1.0a |
| 管理员可审计降低用户信任 | 用户不敢导入敏感文献 | 首次授权明确说明；管理员显式授权；访问留痕；用户可查看记录 |
| 个人派生文本集中存储 | 隐私和服务端成本 | 不存 PDF、不存笔记、可清空、生命周期明确、日志脱敏 |
| 外部模型处理命中片段 | 研究内容离开本地 | 首次知情、供应商可配置、用户可选择不使用全景模式 |
| S2/OpenAlex 限流或字段缺失 | 缺口发现不完整 | 独立降级、来源标注、缓存和重试，不伪造摘要 |
| 联网搜索结果质量不稳定 | 错误背景和引用 | 仅作为 `web_context`，不能单独支撑科学结论，保留来源链接 |
| 可能重新膨胀为中央语料库 | 产品失焦、版权和存储风险 | 旧 57K 已删除；新范围只来自用户授权 Web API；评测使用小型合规 fixtures |
| 分析任务范围蔓延 | 试点延期 | Connector、group libraries、分享、批注/笔记、公共库和本地模型全部延期 |

## 12. 后续路线（不属于 v1 验收，也不是当前排期）

以下仅是候选方向，不构成路线承诺；任何项目进入实施前都必须新增 ADR。

1. 可选 Connector：让用户读取本地-only Zotero 内容，复用 `ZoteroSource` 边界。
2. Group libraries：需要独立设计共享权限、审计和同步责任。
3. Zotero 批注与笔记索引：作为独立的用户授权开关。
4. 公共精选库：当前已排除；若未来重新评估，必须独立解决投稿、版权、审核、治理和版本责任。
5. 本地/自托管模型模式：用于敏感项目。
6. 更丰富的评测基准：覆盖全文问答、缺口发现和引用忠实性。
7. 团队级研究成果管理：必须重新设计分享和权限边界。

## 13. 术语与附录

### 13.1 术语表

| 术语 | 定义 |
|---|---|
| Zotero Web API | Zotero 官方云端 API；v1 唯一 Zotero 接入路径 |
| Connector | 未来可能运行在用户本机、读取 Zotero Local API 的可选程序；不在 v1 |
| Collection | Zotero 中用于组织文献的文件夹 |
| Scope | 本次项目或查询允许检索的 collection 集合 |
| 派生全文 | 从 Web API 可用 fulltext 获得的可检索文本，不是原始 PDF |
| 个人文库 | 用户通过 Web API 已同步并可被系统索引的个人 My Library 范围 |
| 结构化来源 | 提供学术元数据、摘要或引用关系的 API 来源 |
| 联网上下文 | 通用搜索返回的网页背景，可信度低于论文证据 |
| 缺口 | 个人文库相对外部研究现状未覆盖的工作、方法或进展 |
| Planner | 根据问题建议调研模式、来源和阶段的计划组件 |

### 13.3 数据生命周期表

| 事件 | 立即行为 | 30 天行为 | 用户可见性 |
|---|---|---|---|
| Zotero 删除条目 | 退出检索、标记移除 | 清除派生数据 | 状态和回收期可见 |
| 撤销 Web API 连接 | 停止同步、退出检索 | 清除派生数据 | 连接状态可见 |
| 项目/查询 scope 调整 | 退出后续查询范围 | 不清除个人文库索引 | 历史简报保留原 scope |
| 主动清空索引 | 全部清除 | 不保留 | 删除前显示不可逆提示 |
| 删除项目 | 项目不可见 | 清除项目关联数据 | 回收期状态可见 |
| 删除账户 | 撤销会话 | 清除全部派生数据 | 提供删除完成记录 |
