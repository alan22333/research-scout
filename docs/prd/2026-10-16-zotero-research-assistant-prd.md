## 1. 决策摘要

### 1.1 一句话定义

面向信息安全课题组的调研助手：以用户自己的 Zotero 全文库为首要语料，在用户显式选择的研究范围内回答问题、发现库外知识缺口，并联合 Semantic Scholar、OpenAlex 和通用联网搜索形成可核验的研究简报。

### 1.2 背景

现有项目已经验证了“查询改写 → 混合检索 → 重排 → 带引用综合”的技术链路，并建立了一个包含 26 个 venue、57,343 篇论文的中央摘要库。该库证明了垂直检索和生成的可行性，也暴露了三个无法靠继续扩大开发者维护语料库来解决的问题：

1. 摘要无法支撑方法、实验、公式、表格等全文级研究问题。
2. 开发者无法合法、稳定、低成本地获取全领域全文，也无法承诺覆盖完整。
3. 用户真正关心的是“我的文献库里有什么”，而不是一个与个人阅读状态脱节的公共摘要索引。

因此，新产品把个人语料的维护责任交还给文献所有者：Zotero 是用户原文和 collection 的事实源，系统只同步用户明确授权的 collection 并建立派生全文索引。原有 57,343 篇中央摘要库及其向量数据已于 2026-10-16 删除，旧代码仅保留作历史参考，不迁移到新产品。

### 1.3 已确认决策

| 决策项 | 结论 |
|---|---|
| 产品定位 | 课题组基础设施，不是毕业研究原型或个人工具 |
| 首要场景 | 个人 Zotero 全文问答 + 库外缺口发现 |
| 语料来源 | 用户授权的 Zotero collection |
| Zotero 接入 | 仅通过 macOS Connector 读取本地 Zotero Local API；v1 不做 Web API 接入 |
| 同步边界 | 只同步用户选定 collection 的元数据、派生全文、分块和向量 |
| 原文存储 | 原始 PDF 保留在用户本机，服务端不保存 PDF |
| 内容范围 | v1 仅索引论文全文与标准元数据，不索引批注和私人笔记 |
| Zotero 关系 | 只读，不回写、不修改 collection、不删除条目 |
| 核心工作对象 | 研究项目；项目持续保存 scope、提问、简报和反馈 |
| 检索范围 | 每次提问可多选已同步 collection，并可保存常用 scope |
| 检索模式 | 我的文库、查缺补漏、全景调研三档；Planner 只能建议，不能静默升级 |
| 结构化来源 | 首版 Semantic Scholar + OpenAlex；DBLP 延后 |
| 通用联网搜索 | 仅在全景调研模式启用，来源标记为低层级上下文 |
| 输出形式 | 完整研究简报 + 多轮追问 |
| 缺口展示 | 经典/权威、相关方法、最新进展三类并列 |
| 身份权限 | 复用 Lab Nexus；学生与教师功能一致 |
| 管理员审计 | 只有显式系统管理员可审计派生内容；教师不自动获得权限 |
| 私人历史 | 仅本人可见，可删除 |
| 分享协作 | v1 不做站内分享、研究卡片或公共库 |
| 数据生命周期 | Zotero 删除后立即退出检索，30 天后清除派生数据 |
| 模型边界 | 用户允许把命中片段交给配置的 LLM/Embedding API，首次使用明确告知 |
| 试点规模 | 3–5 名真实用户 |
| 客户端范围 | v1 仅支持 macOS Connector |
| 原中央摘要库 | 数据库、向量和 Docker 数据卷已删除；旧代码仅保留作历史参考 |

### 1.4 成功标准

试点以真实任务验证为主：

- 3–5 名用户各完成至少 3 个真实研究问题。
- 70% 的调研任务被用户评价为“对实际问题有帮助”。
- 80% 的研究简报包含可核验、可追溯的引用。
- 至少产生一次“发现库外论文并自行收藏到 Zotero”的真实事件。
- 用户能够理解哪些 collection 已索引、哪些内容同步失败，以及结论来自哪一层证据。

### 1.5 非目标

- 不抓取、不维护、不扩张全领域中央全文或摘要语料库。
- 不保存原始 PDF，不成为第二个 Zotero 或 EndNote。
- 不修改 Zotero 条目、collection、附件或阅读状态。
- v1 不索引 Zotero 批注、高亮、笔记或私人研究想法。
- v1 不做手动单篇 PDF 上传。
- v1 不做站内分享、研究卡片、公共投稿与公共精选库。
- 不承诺覆盖整个信息安全领域，也不承诺穷尽整个互联网。
- 不诊断用户属于哪个年级或角色，学生与教师使用同一套功能。
- 不向用户展示模型隐藏推理，只展示调研计划、工具、来源和证据。

## 2. 目标、原则与用户

### 2.1 产品目标

1. 让用户能够基于自己已经收集和阅读的全文材料提出研究问题。
2. 让每一次回答都能明确追溯到个人全文、结构化摘要或联网上下文。
3. 让用户看见自己的库与外部研究现状之间的差距，而不是得到一个假装完整的答案。
4. 让首次接入、增量同步、失败恢复和删除边界都可理解、可控制。
5. 为后续公共精选库、Windows Connector 和本地模型模式保留清晰边界，但不在 v1 实现。

### 2.2 产品原则

| 原则 | 含义 |
|---|---|
| 个人文库优先 | 默认先回答“我的材料说明了什么”，再判断是否需要外部检索 |
| 范围显式 | 每次提问的 collection 和检索模式都必须可见、可修改 |
| 证据分层 | 个人全文、结构化摘要、联网上下文不能混为同一可信等级 |
| 只读 Zotero | Zotero 是唯一事实源，系统不写回任何内容 |
| 数据最小化 | 不上传 PDF，不收集批注和笔记，只保留完成检索所需的派生数据 |
| 明确失败 | 同步、解析、限流和证据不足必须显式展示，不能静默漏答 |
| 用户可控 | 用户可暂停同步、清理索引、删除项目并查看管理员审计记录 |

### 2.3 用户与权限角色

| 角色 | 定义 | v1 能力 |
|---|---|---|
| 普通用户 | 课题组学生或教师 | 管理自己的 Zotero 连接、项目、scope、历史和数据 |
| 系统管理员 | Lab Nexus 中显式授予的管理员 | 普通用户能力 + 审计派生内容 + 查看审计日志 |
| Lab Nexus | 身份和权限提供方 | 认证、租户身份、角色来源和会话管理 |

教师默认是普通用户，不因为教师身份自动获得学生文库审计权。

### 2.4 Jobs To Be Done

| JTBD | 用户想要的进展 | 产品响应 |
|---|---|---|
| 个人全文问答 | 针对自己读过的论文问方法、实验、结论和区别 | 在选定个人 collection 中做全文检索和带引用综合 |
| 跨 collection 综合 | 把多个方向、多个文件夹的材料放在一起比较 | 支持多选 collection 和保存常用 scope |
| 找漏 | 知道自己的库里缺了哪些关键工作 | Semantic Scholar + OpenAlex 发现并并列展示三类缺口 |
| 进入陌生领域 | 快速了解一个方向的背景、主流方法和时间线 | 全景调研模式加入联网上下文并生成完整简报 |
| 跟踪最新进展 | 查看某方向近期新增工作和变化 | 结构化来源按时间和引用关系展示最新进展 |
| 形成可核验简报 | 得到能继续人工阅读和判断的结构化材料 | 每条关键结论绑定引用，明确未决问题与证据不足处 |

### 2.5 用户痛点与设计回应

- **“我收藏了很多，但真正读过的不多。”**：系统尊重现有 Zotero 结构，不要求用户先整理完才会使用。
- **“我不知道自己的库漏了什么。”**：外部检索与个人库结果分层展示，缺口单独成区。
- **“AI 答案不知道从哪里来。”**：个人全文引用优先，无法支撑时明确说明，不使用无来源的确定性表达。
- **“全文获取困难、存储成本高、覆盖面不可控。”**：原文不集中，开发者不预存语料，系统只处理用户授权的派生文本。
- **“不想再维护一个文献管理器。”**：系统不提供文献增删改和 collection 管理入口。

## 3. 产品范围与信息架构

### 3.1 v1 范围

- Lab Nexus 登录、租户隔离和显式管理员角色。
- macOS Connector 安装、健康检查、collection 授权和增量同步。
- Zotero 全文、标准元数据、附件标识和 collection 隶属关系索引。
- 同步范围、条目数、已索引数、失败原因和最后同步时间展示。
- 研究项目管理、私人历史和可保存的多 collection scope。
- 我的文库、查缺补漏、全景调研三种检索模式。
- 过程可见的调研计划、工具调用、来源和阶段状态。
- Semantic Scholar + OpenAlex 外部发现与结果归一化。
- 完整研究简报、三类缺口和多轮追问。
- 引用追溯、证据分层、外部结果只读与导出。
- 暂停同步、清空索引、删除项目和 30 天数据生命周期。
- 管理员审计与用户可见的审计记录。

### 3.2 v1 明确排除

| 排除项 | 原因 |
|---|---|
| 站内分享和研究卡片 | 不是核心闭环，增加隐私和权限复杂度 |
| 公共精选库 | 需要独立的内容投稿、审核、版权和治理设计 |
| 手动 PDF 上传 | v1 统一通过 Connector 获取 Zotero 全文，避免第二套摄入链路 |
| Zotero 写回 | 保持只读承诺，避免状态冲突 |
| Zotero 批注和笔记 | 用户未将私人阅读信号纳入 v1 范围 |
| 文献管理 CRUD | 继续由 Zotero 承担 |
| Web API 接入 | v1 选择单一 Connector 入口，保证本地读取和体验一致 |
| Windows/Linux Connector | 先验证 macOS 试点，再按真实需求扩展 |
| DBLP | 首版只解决核心发现需求，延后第三来源 |
| 本地自托管模型 | v1 允许外部模型 API，本地模式作为后续增强 |

### 3.3 核心领域对象

| 对象 | 职责 |
|---|---|
| `ZoteroConnection` | 设备、授权状态、Connector 版本、同步状态和健康信息 |
| `CollectionScope` | 一个或多个 Zotero collection；项目默认 scope 与单次查询 scope 分离 |
| `IndexedDocument` | Zotero item/attachment 标识、标准元数据、派生全文和处理状态 |
| `Chunk` | 语义或段落分块、来源位置和向量 |
| `Project` | 用户围绕一个研究主题持续工作的容器 |
| `QuerySession` | 一次包含模式、scope、过程和追问的调研会话 |
| `ResearchBrief` | 一次调研的结构化输出 |
| `Evidence` | 证据及来源层、引用位置和可追溯链接 |
| `Gap` | 个人库相对于外部研究现状的缺口 |
| `AuditEvent` | 管理员访问或数据操作记录 |

固定枚举：

```text
RetrievalMode = my_library | gap_fill | landscape
EvidenceType = personal_fulltext | structured_abstract | web_context
GapType = canonical | related_method | latest_progress
```

### 3.4 信息架构

1. **工作台**：项目列表、最近调研、同步健康状态、待处理问题。
2. **Zotero 连接**：Connector 状态、授权 collection、覆盖情况、暂停与重新同步。
3. **研究项目**：默认 scope、默认模式、历史会话、研究简报和反馈。
4. **提问页**：问题输入、模式选择、多 collection scope、调研预览。
5. **过程页**：计划、当前阶段、工具、来源和降级状态；不展示隐藏推理。
6. **简报页**：结论摘要、证据化发现、方法/时间脉络、三类缺口、未决问题和引用。
7. **私人历史**：仅本人可见，可删除项目或单次会话。
8. **审计记录**：用户查看谁在何时访问了哪些审计数据。
9. **系统管理**：管理员角色、设备撤销、租户配置和运行状态。

## 4. 核心用户旅程

### 4.1 首次使用

1. 用户通过 Lab Nexus 登录。
2. 系统显示独立的数据知情说明：只读 Zotero、不上传 PDF、派生文本集中存储、管理员可审计、外部模型处理范围。
3. 用户下载 macOS Connector。
4. Connector 检查 Zotero 是否安装并运行、Local API 是否可用、版本是否支持。
5. 用户选择一个或多个 collection。
6. 系统开始增量同步并展示处理状态。
7. 用户看到已索引数量、失败数量和不可用原因后，首次创建研究项目。

**完成标准**：用户明确授权至少一个 collection，且至少一篇文档进入可检索状态。

### 4.2 日常调研

1. 用户进入已有项目或创建新项目。
2. 系统默认带入项目 scope，但提问页始终显示本次实际范围。
3. 用户选择我的文库、查缺补漏或全景调研。
4. Planner 生成调研计划；若建议升级模式，必须先获得用户确认。
5. 系统执行检索并展示阶段、工具和来源。
6. 系统输出完整研究简报。
7. 用户继续追问或调整 scope 重新调研。

### 4.3 多轮追问

- 追问继承当前项目的 scope 和检索模式，但允许显式修改。
- 追问可以要求聚焦某篇论文、某个方法或某个缺口。
- 新证据必须追加引用，不得覆盖此前引用的来源。
- 用户改变 scope 或模式时，系统明确标记本次回答使用了新的范围。
- 模型不确定或证据冲突时，展示冲突而不是强行给出单一结论。

### 4.4 库外发现

1. 用户选择查缺补漏或全景调研。
2. 系统检索个人库，并调用 Semantic Scholar、OpenAlex 或联网搜索。
3. 外部结果与个人库结果去重、归一化并分层。
4. 系统并列展示经典/权威、相关方法、最新进展三类缺口。
5. 用户查看 DOI、摘要、引用关系或外部页面。
6. 用户可复制 DOI/BibTeX 或跳转 Zotero；系统不自动写回。

### 4.5 同步失败与恢复

- Zotero 未运行：提示启动 Zotero，保留现有索引和查询能力。
- Local API 不可用：展示原因与修复步骤，不进入无限重试。
- Connector 离线：已有索引可查询，但显示“数据可能过期”和最后同步时间。
- 单篇解析失败：不影响其他文档，记录原因并允许重试或跳过。
- 外部 API 限流：对应来源标记为暂不可用，个人文库模式继续工作。
- 网络中断：增量同步可续跑，重复执行不产生重复文档或重复向量。

## 5. 功能需求

以下功能均为 P0。每项需求必须同时满足业务规则、异常规则和验收条件。

### FR-01 Lab Nexus 身份与租户隔离

**用户故事**：作为课题组成员，我希望用现有 Lab Nexus 账号登录，并且只能访问自己的 Zotero 数据和项目。

**业务规则**

- Lab Nexus 是唯一登录入口，不提供独立密码注册。
- 所有个人数据必须绑定 Lab Nexus 用户和租户。
- 显式系统管理员角色来自 Lab Nexus，不由产品内部自行推断。
- 普通用户不能读取其他用户的项目、scope、派生文本、查询或审计记录。

**异常路径**

- Lab Nexus 不可用时拒绝新登录，但已建立会话按安全策略处理。
- 角色同步失败时采用最小权限，不得自动提升为管理员。

**验收条件**

- 两个普通用户互相访问项目或文档 API 时均被拒绝。
- 教师账号未授予管理员角色时无法审计他人文库。
- 被撤销管理员角色后，新请求立即按普通用户权限处理。

### FR-02 macOS Connector 安装与健康检查

**用户故事**：作为 macOS 用户，我希望一次安装后就能连接 Zotero，并清楚知道环境是否满足要求。

**业务规则**

- Connector 是 v1 唯一 Zotero 接入方式。
- Connector 必须经过代码签名和公证，并支持自动更新。
- Connector 只读取 Zotero Local API，不开放入站监听端口。
- 完成索引后，用户可从任意浏览器查询已有派生数据；Connector 只需在首次接入和增量更新时运行。
- Connector 主动通过 HTTPS 连接应用服务，使用可撤销的设备凭据。
- 安装流程检查 macOS 最低版本、Zotero 版本、Zotero 是否运行和 Local API 可用性。

**异常路径**

- 版本不支持时禁止同步并说明最低要求。
- 设备凭据失效时要求用户重新授权，不继续上传数据。
- Connector 被卸载或长时间离线时，服务端标记连接为离线。

**验收条件**

- 在干净 macOS 环境完成安装、登录、健康检查和设备注册。
- 网络抓包确认 Connector 没有监听外部入站端口。
- 撤销设备后，Connector 无法继续上传派生数据。

### FR-03 Collection 授权与增量同步

**用户故事**：作为用户，我希望只同步我选中的 Zotero collection，并能随时调整范围。

**业务规则**

- 首次同步必须由用户显式选择 collection。
- 用户可以增加或移除 collection。
- 同步只处理选定 collection 中的文献条目及其可读全文。
- 同步必须幂等，重复执行不得产生重复文档、分块或向量。
- Connector 记录同步游标，网络中断后可从断点续跑。

**异常路径**

- attached file 缺失时记录条目状态，但不阻断其他条目。
- collection 在 Zotero 中被重命名时，以稳定标识而不是名称作为主键。
- collection 被移除出授权范围时，其文档立即退出当前检索范围。

**验收条件**

- 连续运行两次同步，文档和向量数量不增加重复行。
- 中断同步后重新执行，只补传未完成内容。
- 移除一个 collection 后，其结果不再出现在我的文库模式中。

### FR-04 全文与元数据索引

**用户故事**：作为用户，我希望系统能回答论文方法、实验和结论问题，而不是只看摘要。

**业务规则**

- 只索引 Zotero Local API 可读取的全文内容。
- 标准元数据至少包含标题、作者、年份、venue、DOI/Zotero item key 和 attachment key。
- 服务端保存派生全文、分块、向量和元数据，不保存 PDF 二进制。
- 分块需保留论文内来源位置；位置不可可靠获取时至少保留文档级追溯。
- 同一论文以 DOI 优先、其次稳定学术标识、最后标题与年份归一化去重。

**异常路径**

- 无全文时标记为“仅有元数据”，不得用摘要冒充个人全文。
- 解析质量低时标记失败或需复核，不进入高可信全文证据层。
- 同一论文出现在多个 collection 时，只保留一个文档实体并维护多个 scope 关系。

**验收条件**

- 对本地-only PDF 能生成可检索全文，并确认对象存储中不存在对应 PDF。
- 同一 DOI 在个人库和外部来源中出现时不会重复引用。
- 方法或实验问题能命中正文分块，而不仅是标题或摘要。

### FR-05 索引覆盖与状态展示

**用户故事**：作为用户，我希望知道哪些 collection 和文献已经索引，哪些还没有。

**业务规则**

- 按 collection 展示条目数、已索引数、仅有元数据数、失败数和最后同步时间。
- 失败必须给出可理解原因和下一步操作。
- Connector 离线时展示陈旧标记，不假称数据最新。
- 覆盖状态只描述当前授权范围，不承诺覆盖整个研究领域。

**异常路径**

- 状态未知时显示“未知”，不得用 0 或已完成代替。
- 部分同步完成时展示部分成功，不将整体标记为成功或失败。

**验收条件**

- 同步过程中可实时看到进度和已完成数量。
- 任一失败条目都能在界面上定位并触发重试。
- Connector 停止后超过同步周期，界面显示“数据可能过期”。

### FR-06 研究项目管理

**用户故事**：作为研究者，我希望围绕一个研究主题持续提问和积累简报。

**业务规则**

- 用户可以创建、重命名、归档和删除项目。
- 项目保存默认 collection scope、默认检索模式和历次会话。
- 项目不复制文献，不形成独立文献库。
- 项目历史默认仅本人可见。
- 项目可以包含多轮查询、简报和用户反馈。

**异常路径**

- 项目引用的 collection 被取消授权后，该项目标记 scope 失效并要求重选。
- 项目删除后立即从产品列表消失，后台生命周期按数据删除规则执行。

**验收条件**

- 同一项目连续进行多轮调研，历史引用不丢失。
- collection 失效后不能继续使用旧 scope 静默查询。
- 另一个普通用户无法通过链接或接口访问项目。

### FR-07 多 Collection Scope

**用户故事**：作为用户，我希望每次提问时选择多个 collection，并保存常用组合。

**业务规则**

- 单次查询支持选择一个或多个已同步 collection。
- 项目可以设置默认 scope，但提问页必须显示本次实际 scope。
- 用户可以保存常用 scope 作为项目内快捷选项。
- 未授权、已删除或同步失败的 collection 不能静默参与检索。

**异常路径**

- scope 为空时阻止提交，并引导选择 collection。
- scope 中部分 collection 失效时，提交前要求用户确认或移除。
- 新输入范围与项目默认范围不同时，在简报中记录实际范围。

**验收条件**

- 多选 collection 的查询能命中各 collection 中的相关全文。
- 修改项目默认 scope 不改变历史简报记录的范围。
- 保存的 scope 可以复用、编辑和删除。

### FR-08 三种检索模式

**用户故事**：作为用户，我希望根据任务选择只查个人库、查缺补漏或做全景调研。

**业务规则**

| 模式 | 检索范围 | 主要用途 |
|---|---|---|
| 我的文库 `my_library` | 个人已索引全文 | 个人材料问答、跨 collection 综合 |
| 查缺补漏 `gap_fill` | 个人全文 + S2/OpenAlex | 发现经典工作、相关方法和最新进展 |
| 全景调研 `landscape` | 个人全文 + S2/OpenAlex + 通用联网搜索 | 陌生主题、背景和行业现状扫描 |

- 每次提问前显式选择模式。
- Planner 可以建议切换模式，但必须由用户确认。
- 外部来源失败时不得降低个人文库查询结果的可信度。
- 简报必须记录实际使用的模式。

**验收条件**

- 我的文库模式不发出外部学术或联网搜索请求。
- 查缺补漏模式不调用通用联网搜索。
- 全景调研模式对联网来源做低层级证据标注。
- Planner 建议升级后未确认时，系统仍执行原模式。

### FR-09 结构化外部发现

**用户故事**：作为用户，我希望借助 Semantic Scholar 和 OpenAlex 找到个人库遗漏的重要论文。

**业务规则**

- Semantic Scholar 负责语义发现、引用关系和论文标识。
- OpenAlex 负责元数据、摘要、DOI 和来源补充。
- 外部结果必须归一化后再与个人库去重。
- 每个结果展示来源、年份、venue、DOI 和可追溯链接。
- DBLP、Crossref 和其他来源不在 v1 产品承诺内，但接口应允许后续增加适配器。

**异常路径**

- S2 限流时展示结构化来源暂不可用，并允许稍后重试。
- OpenAlex 缺少摘要时保留元数据，不伪造摘要。
- 外部结果冲突时同时展示来源并标记冲突，不静默选择。

**验收条件**

- 同一 DOI 在 S2、OpenAlex 和个人库中只出现一个规范化论文实体。
- 任一外部来源失败时，其他来源和个人库结果仍可展示。
- 外部结果不会进入个人全文证据层。

### FR-10 通用联网搜索

**用户故事**：作为用户，我希望在全景调研时补充网页背景，但能清楚区分网页内容和论文证据。

**业务规则**

- 仅在全景调研模式启用。
- 搜索结果必须包含可访问来源链接和抓取时间。
- 网页内容标记为 `web_context`，不能单独支撑科学事实结论。
- 不把整页网页永久保存为语料；只保留实现引用所需的摘要、链接和元数据。
- 用户问题中如果包含敏感内容，系统需在首次使用时告知查询会发送给外部搜索与模型服务。

**异常路径**

- 搜索供应商不可用时标记该层降级，不阻断个人文库与结构化来源。
- 网页内容与论文结论冲突时优先展示论文证据并注明冲突。

**验收条件**

- 关闭或未配置搜索供应商时，前两种模式完全可用。
- 联网来源在简报中具有独立标签和链接。
- 删除会话后，非必要网页上下文按生命周期规则清除。

### FR-11 完整研究简报

**用户故事**：作为用户，我希望得到一份能直接用于调研讨论的结构化简报。

**业务规则**

默认固定包含：

1. 结论摘要。
2. 按主题组织的证据化发现。
3. 方法分类与时间脉络。
4. 三类缺口：经典/权威工作、相关方法、最新进展。
5. 当前证据无法回答的问题。
6. 引用与证据列表。

- 每条关键结论必须绑定至少一个引用锚点。
- 个人全文、结构化摘要、联网上下文必须分层标注。
- 证据不足时明确说明，不使用确定性语言补全。
- 简报保留本次 scope、模式、来源和生成时间。

**验收条件**

- 随机抽样关键结论可追溯到具体文档和分块。
- 取下任一关键引用后，对应结论应被标记为证据不足，而不是保持原样。
- 简报能够显示三类缺口，且不把“未找到”误写成“领域不存在”。

### FR-12 多轮追问

**用户故事**：作为用户，我希望继续追问某篇论文、某类方法或某个缺口，而不必重新描述背景。

**业务规则**

- 追问继承当前项目的 scope 和模式，但界面显示继承状态。
- 用户可以显式修改 scope 或模式。
- 新证据追加到证据列表，不覆盖历史来源。
- 追问可以引用已有结论、论文、证据或缺口作为上下文。
- 用户改变范围后，简报明确标记“本次使用了新的检索范围”。

**验收条件**

- 连续 3 轮追问后，原始引用仍可访问。
- 修改 scope 后，系统不会把旧范围结果误标为新范围结果。
- 追问不能访问用户未授权的 collection。

### FR-13 证据分层与引用追溯

**用户故事**：作为用户，我希望知道一条结论究竟来自我的全文、外部摘要，还是网页背景。

**业务规则**

| 证据层 | 类型 | 可作为科学结论依据 |
|---|---|---|
| 个人全文 | `personal_fulltext` | 是，最高优先级 |
| 结构化摘要 | `structured_abstract` | 是，但必须标注限于摘要 |
| 联网上下文 | `web_context` | 否，只能提供背景或线索 |

- 引用应包含论文标题、来源、年份、DOI/URL 和文档内定位。
- 定位信息不稳定时，至少追溯到论文级。
- 引用冲突时展示不同来源和冲突点。
- 用户点击引用可回到 Zotero item、DOI 或外部页面。

**验收条件**

- 只依赖联网上下文时不能生成无保留的科学事实结论。
- 结构化摘要与个人全文冲突时，系统提示冲突并显示两者。
- 引用链接失效时保留规范标识和最后验证时间。

### FR-14 外部结果只读与导出

**用户故事**：作为用户，我希望把发现的论文带回自己的研究工作流，但不让系统擅自修改 Zotero。

**业务规则**

- 外部结果支持复制 DOI、复制 BibTeX、打开出版商页面和打开 Zotero。
- 系统不自动写入 Zotero，不创建 collection，不下载并托管 PDF。
- 用户可以手动把论文加入 Zotero；下次同步后自然进入个人语料。

**异常路径**

- DOI 或链接无效时显示原始来源记录和最后验证时间。
- 用户未安装 Zotero 时提供 DOI/BibTeX 导出，不阻断结果查看。

**验收条件**

- 产品界面不存在自动写回 Zotero 的入口。
- 复制出的 DOI/BibTeX 可被 Zotero 正常导入。
- 外部结果不会改变个人库 scope 或索引。

### FR-15 私人历史与反馈

**用户故事**：作为用户，我希望查看自己的调研历史，并告诉系统哪条结果有用或遗漏。

**业务规则**

- 历史默认仅本人可见，不因管理员存在而对普通用户展示为共享空间。
- 用户可以打开、重命名、归档和删除自己的项目或会话。
- 反馈类型至少包括“有帮助”“不相关”“疑似遗漏”。
- 反馈可以用于评测和后续功能优化，但不能在未经用户操作时自动扩大语料。
- v1 不提供分享链接或协作权限。

**验收条件**

- 普通用户无法搜索、列出或访问他人历史。
- 删除会话后，历史列表和检索结果中均不再出现。
- 反馈不会直接把外部论文写入个人库。

### FR-16 删除、清空与数据生命周期

**用户故事**：作为用户，我希望删除行为符合我的预期，并能从误操作中恢复。

**业务规则**

| 事件 | 活跃索引 | 派生数据保留 | 最终清理 |
|---|---|---|---|
| Zotero 删除条目 | 立即移除 | 30 天回收期 | 30 天后清除 |
| collection 移出授权范围 | 立即移除 | 30 天回收期 | 30 天后清除 |
| 用户主动清空索引 | 立即清空 | 不保留回收期 | 确认后立即清除 |
| 删除项目或会话 | 立即不可见 | 30 天回收期 | 30 天后清除 |
| 删除账户 | 立即撤销设备和会话 | 30 天回收期 | 30 天后清除全部派生数据 |

- 清理范围包括派生全文、分块、向量、项目范围关系和查询关联。
- 清理不删除用户 Zotero 中的任何内容。
- 用户必须在清空索引前看到影响范围和不可逆提示。

**验收条件**

- Zotero 删除后的下一个同步周期，文档不再出现在检索结果中。
- 30 天后数据库中不存在对应派生文本和向量。
- 主动清空索引后立即无法通过任何历史接口恢复内容。
- 删除 Zotero 文档不会反向删除 Zotero 条目。

### FR-17 管理员审计

**用户故事**：作为系统管理员，我需要在系统安全事件或合规要求下审计派生内容，但权限必须明确且留痕。

**业务规则**

- 只有 Lab Nexus 显式管理员可进入审计功能。
- 审计范围包括用户、collection、文档元数据、派生文本、查询和审计事件。
- 原始 PDF 不在服务端，因此管理员无法通过系统获取 PDF。
- 每次访问必须记录管理员、时间、对象、原因和请求标识。
- 用户可以查看与自己相关的管理员访问记录。
- 普通教师不能因为职称自动获得管理员权限。

**异常路径**

- 管理员会话过期时重新认证，不延长普通用户会话。
- 审计日志写入失败时阻止敏感内容访问。

**验收条件**

- 普通用户和教师默认看不到审计入口。
- 每次管理员查看派生内容都会生成可见记录。
- 撤销管理员角色后，访问被实时拒绝。

### FR-18 降级、重试与可观测性

**用户故事**：作为用户，我希望系统在部分依赖失败时继续可用，并明确告诉我缺了什么。

**业务规则**

- 个人文库检索不依赖外部搜索，外部来源失败时继续工作。
- 同步和外部检索必须支持有限重试、退避和断点续跑。
- 任何失败不得被包装为“没有结果”。
- 界面显示当前阶段、完成的来源、跳过的来源和失败原因。
- 运行日志不得记录完整私人全文或个人查询原文，除非用户明确启用调试并知情同意。

**验收条件**

- 切断 S2 后，我的文库模式仍能完整回答个人库问题。
- 切断网络后，Connector 恢复时从断点继续。
- 外部来源失败时，简报显示“该来源不可用”，而不是零结果结论。
- 日志抽查不包含完整 PDF 文本。

## 6. 检索、证据与回答规则

### 6.1 模式矩阵

| 能力 | 我的文库 | 查缺补漏 | 全景调研 |
|---|:---:|:---:|:---:|
| 个人全文 RAG | ✓ | ✓ | ✓ |
| Semantic Scholar |  | ✓ | ✓ |
| OpenAlex |  | ✓ | ✓ |
| 通用联网搜索 |  |  | ✓ |
| 缺口清单 |  | ✓ | ✓ |
| 方法与时间脉络 | ✓ | ✓ | ✓ |
| 联网背景 |  |  | ✓ |

### 6.2 检索编排

1. 解析用户问题，提取主题、时间、方法和比较意图。
2. 读取用户显式选择的 scope 和模式。
3. 在个人全文索引中执行混合检索和重排。
4. 查缺补漏和全景调研模式继续调用结构化来源。
5. 全景调研模式在需要背景时调用联网搜索。
6. 去重、归一化、按证据层级重组候选集。
7. 判断证据是否足以支持结论；不足时生成未决问题和缺口，而不是补写。
8. 输出完整研究简报并记录来源与工具状态。

Planner 可以建议模式或补充 scope，但产品必须展示建议并要求用户确认。

### 6.3 缺口判定

三类缺口并列展示，不设置固定统一优先级：

- **经典/权威工作**：高引用、综述、领域共识或重要里程碑。
- **相关方法**：与问题相关但用户库未覆盖的方法、任务或应用场景。
- **最新进展**：用户库没有覆盖的近期论文、趋势或新问题。

每条缺口必须说明它相对哪个范围存在：缺失于个人库、缺失于本次 collection scope，或仅由外部来源发现。不能把“当前检索未命中”直接表述为“领域不存在”。

### 6.4 引用与诚实性

- 关键结论必须引用证据。
- 引用必须支持该结论，不能仅做关键词相关。
- 个人全文引用优先于结构化摘要，结构化摘要优先于联网上下文。
- 联网上下文只能提供背景、术语或外部线索。
- 证据冲突、来源失效、摘要缺失和解析失败必须显式展示。
- 不展示隐藏推理链，只展示可验证的计划、步骤、工具和证据。

## 7. 数据、权限与安全

### 7.1 数据清单

| 数据 | 所在位置 | 服务端是否保存 | 用途 |
|---|---|---:|---|
| 原始 PDF | 用户本机 Zotero | 否 | 全文来源 |
| Zotero item/attachment 标识 | 服务端 | 是 | 同步、去重和追溯 |
| 标准论文元数据 | 服务端 | 是 | 检索、引用和展示 |
| 派生全文 | 服务端 | 是 | 个人全文检索 |
| 分块与向量 | 服务端 | 是 | 语义检索 |

### 7.3 隐私与信任承诺

首次授权页面必须使用不含糊的语言说明：

> 本服务不会上传或保存你的原始 PDF，也不会修改 Zotero。为了提供检索和问答，服务端会保存你授权 collection 的派生全文、分块、向量和元数据。命中片段可能发送给配置的 LLM/Embedding 服务。个人文库不是端到端私密空间，Lab Nexus 显式系统管理员可以审计派生内容；管理员访问会留下记录，你可以在产品内查看。你可以随时暂停同步、清理索引或删除账户。

### 7.4 安全要求

- Web 与 Connector 通信只允许 HTTPS。
- Connector 使用设备级、可撤销凭据；用户会话不得直接作为长期设备凭据。
- 服务端按租户隔离存储和检索，所有访问在服务端鉴权。
- 管理员访问必须重新认证并记录审计事件。
- 敏感配置和 API 密钥不得写入仓库或前端。
- 日志、监控和分析事件不得包含完整私人全文。
- 删除操作必须在活跃索引、缓存、向量存储和查询历史中一致执行。

## 8. 非功能需求

### 8.1 平台与兼容性

- v1 Connector 仅支持 macOS。
- 最低 macOS 与 Zotero 版本由技术设计确认，但必须支持官方 Local API 读取能力。
- Web 应用支持常用现代浏览器的最新稳定版本。
- Connector 必须支持签名、公证、自动更新和安全卸载。

### 8.2 可靠性

- 同步必须幂等、可恢复，不因网络或 Connector 重启丢失游标。
- 单篇文档失败不得阻断整个 collection 同步。
- 外部来源失败不得阻断个人文库查询。
- 关键任务必须记录脱敏结构化日志，支持定位失败阶段和对象。
- 任何自动重试必须有上限，并向用户展示当前状态。

### 8.3 体验与过程透明

- 用户提交问题后 1 秒内看到受理状态。
- 长任务至少每 5 秒更新一次阶段状态，或明确显示等待外部服务。
- 调研过程必须展示计划、阶段、工具和来源。
- 不展示不可验证的隐藏推理。
- 用户离开页面后重新进入，应能看到进行中或已完成的会话状态。

### 8.4 可维护性与扩展性

- 外部学术来源和联网搜索通过适配器边界接入，避免业务逻辑绑定单一供应商。
- 新增来源不得改变证据分层和用户模式定义。
- 领域对象必须支持租户、用户、项目和来源隔离。
- 未来增加 Windows Connector、批注/笔记和公共库时，不需要推翻个人文库边界。

### 8.5 成本与容量

- 服务端只存储派生数据，容量按文本、分块和向量估算，不包含 PDF。
- 索引任务必须支持限流、并发控制和失败续跑。
- 外部模型和搜索调用必须可观测，避免无限重试造成成本失控。
- v1 不设置硬性响应时长目标，但必须避免依赖故障导致无限等待。

### 9.2 追踪矩阵

| 用户目标 | 功能需求 | 验收场景 | 指标 |

### 9.3 验收用例

1. **首次接入**：新用户安装 Connector，选择两个 collection，完成首次同步并成功提问。
2. **本地-only PDF**：Zotero 中存在未同步到云端的本地 PDF，能够被索引并参与回答。
3. **全文问题**：提问论文方法、数据集或实验结论，回答引用正文分块而非仅标题。
4. **三档模式**：验证各模式只调用允许的来源。
5. **引用追溯**：随机抽样关键结论，确认可回到 Zotero item、DOI 或外部 URL。
6. **多 collection**：选择一个以上 collection，确认结果来自目标范围并记录实际 scope。
7. **外部降级**：切断 S2/OpenAlex/搜索服务，确认个人文库仍可用且界面明确标注来源失败。
8. **同步恢复**：同步中断后重新连接，确认从断点续传且没有重复数据。
9. **生命周期**：删除 Zotero 条目、移除 collection、主动清空索引和删除账户，分别验证活跃索引与 30 天清理。
10. **权限与审计**：普通用户互相隔离；教师未授权不可审计；管理员访问生成用户可见记录。
11. **隐私验证**：确认服务端和对象存储中没有 PDF 二进制，日志中没有完整私人全文。
12. **陈旧状态**：Connector 离线超过同步周期后，界面标记数据可能过期。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Connector 安装门槛导致用户流失 | 无法形成真实语料 | 原型先验证安装流程；目标首次接入成功率 ≥80%；提供清晰错误恢复 |
| 管理员可审计降低用户信任 | 用户不敢导入敏感文献 | 首次授权明确说明；管理员显式授权；访问留痕；用户可查看记录 |
| Zotero Local API 或版本兼容变化 | 无法读取本地全文 | 版本检测、兼容矩阵、签名更新和失败降级 |
| 个人派生文本集中存储 | 隐私和服务端成本 | 不存 PDF、不存笔记、可清空、生命周期明确、日志脱敏 |
| 外部模型处理命中片段 | 研究内容离开本地 | 首次知情、供应商可配置、用户可选择不使用全景模式 |
| S2/OpenAlex 限流或字段缺失 | 缺口发现不完整 | 独立降级、来源标注、缓存与重试，不伪造摘要 |
| 联网搜索结果质量不稳定 | 错误背景和引用 | 仅作为 `web_context`，不能单独支撑科学结论，保留来源链接 |
| 可能重新膨胀为中央语料库 | 产品失焦、版权和存储风险 | 旧 57K 已删除；新范围只来自用户授权 Zotero；评测使用小规模合规 fixtures；公共库独立立项 |
| 分析任务范围蔓延 | 试点延期 | 分享、公共库、批注/笔记、Windows 和本地模型全部延期 |
